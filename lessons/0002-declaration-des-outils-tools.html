Donner des Mains au Modèle : Déclaration des Outils (tools[] & JSON Schema)

Un LLM seul ne peut que prédire des tokens textuels. Pour le transformer en agent capable d'inspecter un dépôt Git ou d'éditer du code, il faut lui exposer des signatures de fonctions formelles.

📖 Fil Rouge Architectural • Chapitre 2
À l'Étape 1, nous avons établi une communication HTTP stateless avec le LLM. Mais dès que nous lui demandons « Quels fichiers ont été modifiés dans mon dépôt local ? », nous nous heurtons à un mur : hébergé sur un serveur distant, le modèle est totalement aveugle face à notre système de fichiers. Comment lui donner connaissance des fonctions exécutables sur notre poste ?
🔴 Le Problème Technique
Un modèle de langage est un cerveau isolé dans un bocal : il n'a ni accès disque, ni socket réseau local, ni terminal Bash. Si on lui demande en langage naturel d'inventer une commande à exécuter sans contrat strict, il hallucine des noms de fonctions inexistants ou passe des paramètres mal typés qui font planter le runtime local.
🟢 La Solution Architecturale
Le client injecte dans la requête HTTP un catalogue déclaratif tools[]. Chaque outil y est spécifié par un contrat JSON Schema (Draft 7 / 2020-12) définissant son identifiant (name), sa sémantique d'invocation (description) et le typage strict de ses paramètres d'entrée (parameters).

1. La Spécification d'un Outil dans le Payload HTTP

Lorsqu'OpenCode ou Cursor envoie votre prompt au LLM, il joint dans le corps JSON le tableau tools[]. Le modèle ne reçoit jamais le code source de l'outil : il ne reçoit que son interface (signature + JSON Schema).

2. Du Code TypeScript au JSON Schema : Comprendre Bun et Zod

Si vous inspectez le code source d'OpenCode ou de ses plugins (que nous coderons à l'Étape 10), vous constaterez qu'aucun développeur n'écrit manuellement les 30 lignes de JSON Schema ci-dessus. OpenCode repose sur deux briques fondamentales de l'écosystème TypeScript moderne : Bun et Zod.

🥟 Qu'est-ce que Bun ? (Le Runtime JS/TS)

Bun est un environnement d'exécution (runtime) JavaScript et TypeScript ultra-rapide qui remplace à la fois Node.js, le compilateur tsc et le gestionnaire de paquets npm.

  • Exécution TypeScript native : Bun exécute directement les fichiers .ts sans étape de compilation préalable.
  • Démarrage instantané (~5 ms) : Idéal pour un agent CLI/TUI comme OpenCode et pour charger des plugins locaux à la volée.
  • BunShell ($) intégré : Permet de lancer des commandes système (git, ripgrep) directement en TypeScript de manière sécurisée.
💎 Qu'est-ce que Zod ? (Le Générateur de Schéma)

Zod est la bibliothèque standard en TypeScript pour déclarer et valider des schémas de données. Dans un agent IA, Zod remplit un double rôle :

  • 1. Avant la requête HTTP (Sérialisation) : Convertit automatiquement votre code TypeScript en JSON Schema injecté dans tools[].
  • 2. Au retour du LLM (Validation Runtime) : Vérifie que le JSON généré par le LLM respecte strictement les types attendus (string, integer, champs obligatoires) avant d'exécuter l'outil !

Exemple Concret : 5 lignes de Zod vs 25 lignes de JSON Schema

Voici comment le même outil read est écrit par le développeur avec Zod (à gauche) et ce qu'OpenCode envoie automatiquement sur le réseau dans tools[] (à droite) :

💎 1. Ce que vous écrivez en TypeScript avec Zod
import { z } from "zod"

// Déclaration concise, typée et auto-documentée avec .describe()
const ReadToolSchema = z.object({
  filePath: z
    .string()
    .describe("Chemin du fichier à lire (ex: src/auth.ts)"),
  offset: z
    .number()
    .int()
    .optional()
    .describe("Numéro de la ligne de départ (commence à 0)"),
  limit: z
    .number()
    .int()
    .optional()
    .describe("Nombre maximum de lignes à retourner"),
})

// Conversion automatique en JSON Schema (Zod v4 natif ou zodToJsonSchema en v3) :
const jsonSchema = z.toJSONSchema(ReadToolSchema)

3. Les Paramètres de Contrôle : tool_choice et parallel_tool_calls

  • "tool_choice": "auto" (défaut) : Le modèle décide de manière autonome s'il doit répondre en texte libre ou demander l'exécution d'un outil.
  • "tool_choice": "none" : Interdit au modèle d'appeler un outil (équivalent d'un mode purement conversationnel).
  • "tool_choice": "required" : Force le modèle à appeler au moins un outil du catalogue.
  • "tool_choice": {"type": "function", "function": {"name": "read"}} : Contraint le modèle à appeler spécifiquement l'outil nommé.
  • "parallel_tool_calls": true (défaut) : Autorise le modèle à émettre plusieurs appels d'outils simultanés en un seul tour (ex: lire src/auth.ts et tests/auth.test.ts en parallèle).
  • "strict": true (optionnel dans tools[].function) : Active le Constrained Decoding d'OpenAI sur les arguments de la fonction pour garantir mathématiquement qu'aucun paramètre requis ne soit omis (mécanisme détaillé à l'Étape 11).

4. Comparaison des Outils Natifs (Built-in Tools) : OpenCode vs Cursor

Sans aucune extension installée, OpenCode et Cursor embarquent chacun une boîte à outils native pré-déclarée dans tools[] :

Catégorie d'Action Outils Natifs OpenCode (Documentation Officielle) Outils Natifs Cursor (Agent Mode)
Lecture de fichiers read (lecture paginée avec offset / limit) read_file (lecture par plage de lignes)
Modification de code edit (remplacement exact de bloc), write, patch edit_file (appliqué via modèle rapide de Fast Apply)
Recherche textuelle & Arborescence grep (basé sur ripgrep), glob, list grep_search, file_search, codebase_search (recherche vectorielle par embeddings)
Exécution Shell bash (exécute une commande dans le PTY/Shell local) run_terminal_cmd (exécute dans le terminal intégré VS Code)
Web & Sous-tâches webfetch, websearch, task (délégation sous-agent), skill, todowrite web_search, délégation vers sous-agents configurés dans .cursor/agents/
