L'Intention d'Action : Intercepter finish_reason: "tool_calls" & Streaming SSE

Le LLM a reçu notre question et notre catalogue tools[]. Que renvoie-t-il exactement sur le réseau lorsqu'il décide d'appeler un outil, et comment le runtime distingue-t-il une réponse finale d'une demande d'action ?

📖 Fil Rouge Architectural • Chapitre 3
À l'Étape 2, nous avons déclaré l'outil read dans tools[] et demandé au modèle de lire src/auth.ts. Le serveur d'inférence distant ne peut évidemment pas lire le disque dur de notre machine. Il doit donc mettre sa génération en pause et déléguer l'exécution au client. Voyons comment ce signal d'interruption est encodé dans la réponse HTTP et dans un flux Server-Sent Events (SSE).
🔴 Le Problème Technique
Lorsque le serveur LLM répond au client, comment l'agent (OpenCode ou Cursor) sait-il s'il doit afficher un message final à l'utilisateur ou s'il doit intercepter la réponse, parser des arguments JSON, exécuter un processus local et relancer une requête ? De plus, en mode Streaming (SSE), les arguments JSON arrivent découpés token par token !
🟢 La Solution Architecturale
Le protocole utilise un discriminant d'état explicite : "finish_reason": "tool_calls" (au lieu de "stop"). Le message assistant contient alors un tableau structuré tool_calls[] associant un identifiant unique de corrélation (id), le nom de la fonction (name) et ses arguments sérialisés (arguments). En mode SSE, le client accumule les fragments delta.tool_calls dans un buffer mémoire jusqu'au signal de fin.

2. Les Valeurs du Discriminant finish_reason

Tout moteur d'agent implémente un automate à états finis (State Machine) piloté par choices[0].finish_reason :

Valeur de finish_reason Signification Protocolaire Action du Runtime (OpenCode / Cursor)
"stop" Le modèle a terminé sa réponse naturelle. Affiche la réponse finale à l'utilisateur et met la session à l'état idle (en attente du prochain prompt).
"tool_calls" Le modèle s'est mis en pause et demande l'exécution d'un ou plusieurs outils locaux. Parse tool_calls[], vérifie les permissions, exécute les outils localement et relance immédiatement la boucle (Étape 4).
"length" Troncature : la limite max_tokens / max_completion_tokens a été atteinte au milieu de la génération. Alerte de troncature (attention : si cela survient pendant un tool_call, la chaîne JSON arguments est incomplète et invalide !).
"content_filter" Interruption par un classifieur de sécurité du fournisseur. Affiche une erreur de refus de politique de contenu.

3. Sous le Capot du Serveur (vLLM / OpenAI) : Exemple Complet d'un Appel d'Outil en 7 Étapes (JSON ↔ ChatML)

Comme nous l'avons découvert à l'Étape 1, le réseau de neurones sur le GPU ne lit et n'écrit que du texte plat (des tokens). Comment fait-il alors pour recevoir votre tableau JSON tools[], produire un objet tool_calls et comprendre un retour role: "tool" ?

Suivons de bout en bout les 7 étapes exactes qui dissocient la « magie » mathématique du LLM (prédiction de texte plat) de la tuyauterie du serveur d'inférence (conversion JSON ↔ ChatML), sur l'exemple : « Quel temps fait-il à Lyon ? »

Détail Pas-à-Pas des 7 Étapes de Traduction

📦 1. La requête applicative (JSON HTTP)

Votre application envoie une structure JSON standard au serveur d'inférence (messages[] + description de get_weather dans tools[]) :

{
  "model": "gpt-4o-mini",
  "messages": [
    { "role": "system", "content": "Tu es un assistant." },
    { "role": "user", "content": "Quel temps fait-il à Lyon ?" }
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "Météo par ville",
        "parameters": { "city": "string" }
      }
    }
  ]
}
🧬 2. L'aplatissement (Le Chat Template Jinja2)

Le moteur du serveur (via Jinja2) écrase ce JSON en un flux de texte brut structuré par les balises du modèle. Le LLM ne voit que ceci :

<|im_start|>system
Tu es un assistant. Tu as accès aux outils suivants :
[{"name": "get_weather", "description": "Météo par ville", "parameters": {"city": "string"}}]<|im_end|>
<|im_start|>user
Quel temps fait-il à Lyon ?<|im_end|>
<|im_start|>assistant
🧠 3. La génération sur le GPU (Prefill → Decode)

En lisant ce texte (Prefill → KV Cache), le réseau de neurones détecte la question et l'outil. Il génère la syntaxe d'appel (Decode) et s'arrête :

<tool_call>
{"name": "get_weather", "arguments": {"city": "Lyon"}}
</tool_call><|im_end|>
🔄 4. Le parsing par le serveur (Traduction JSON)

Le serveur d'inférence intercepte la balise <tool_call> avant affichage, la reformate en JSON classique (finish_reason: "tool_calls") et la renvoie :

{
  "choices": [
    {
      "finish_reason": "tool_calls",
      "message": {
        "role": "assistant",
        "content": null,
        "tool_calls": [
          {
            "id": "call_lyon_01",
            "type": "function",
            "function": {
              "name": "get_weather",
              "arguments": "{\"city\":\"Lyon\"}"
            }
          }
        ]
      }
    }
  ]
}

5. L'exécution physique (Côté Application) :
C'est votre code (et non le LLM) qui exécute la vraie requête HTTP vers l'API Météo (ou qui lit le fichier sur le disque). L'API Météo vous répond "18°C, ensoleillé".

6. La mise à jour de l'historique & le ré-aplatissement (<tool_response>) :
Vous rajoutez ce résultat dans le tableau JSON sous forme de message (avec "role": "tool", que nous détaillerons à l'Étape 4) et vous renvoyez tout l'historique au serveur. Le serveur ré-aplatit l'ensemble : 

... [historique précédent des étapes 2 et 3] ...
<|im_start|>user
<tool_response>
{"temperature": "18°C", "condition": "ensoleillé"}
</tool_response><|im_end|>
<|im_start|>assistant
⚡ Note d'optimisation matérielle — Le KV Cache (Prefix Caching) :
Pourquoi renvoyer tout l'historique à l'Étape 6 n'est-il pas catastrophique en temps de calcul ? Grâce au KV Cache généré à l'Étape 2 ! Comme le début du texte (le prompt system, les définitions d'outils et la question initiale) est strictement identique mot pour mot, le GPU conserve ces matrices en mémoire vidéo (Automatic Prefix Caching dans vLLM / Prompt Caching chez OpenAI) et ne calcule que les nouveaux tokens de la réponse météo <tool_response> !

7. La réponse finale :
Le LLM lit cette nouvelle donne et conclut naturellement : 

Il fait actuellement 18°C et le temps est ensoleillé à Lyon.<|im_end|>

Le serveur retire la balise <|im_end|>, encapsule la phrase dans choices[0].message.content avec "finish_reason": "stop", et votre application l'affiche enfin à l'utilisateur.

4. Reconstruction des Tool Calls en Streaming (Server-Sent Events - SSE)

En conditions réelles, OpenCode et Cursor activent "stream": true pour afficher le texte en temps réel. Lorsqu'un outil est appelé en streaming, la chaîne JSON arguments est transmise par petits fragments (chunks) dans delta.tool_calls :

# Chunk 1 : Annonce du tool_call (id + nom de la fonction)
data: {"choices":[{"index":0,"delta":{"role":"assistant","tool_calls":[{"index":0,"id":"call_abc123xyz","type":"function","function":{"name":"read","arguments":""}}]}}]}

# Chunk 2 : Premier fragment de la chaîne JSON arguments
data: {"choices":[{"index":0,"delta":{"tool_calls":[{"index":0,"function":{"arguments":"{\"filePath\":"}}]}}]}

# Chunk 3 : Suite et fin de la chaîne JSON arguments
data: {"choices":[{"index":0,"delta":{"tool_calls":[{"index":0,"function":{"arguments":"\"src/auth.ts\",\"limit\":50}"}}]}}]}

# Chunk 4 : Signal de fin d'étape indiquant qu'il faut exécuter l'outil
data: {"choices":[{"index":0,"delta":{},"finish_reason":"tool_calls"}]}
data: [DONE]

Pourquoi chaque fragment SSE porte-t-il un "index": 0 dans delta.tool_calls ?
Lorsque "parallel_tool_calls": true (Étape 2) est actif, le LLM peut décider d'appeler 2 ou 3 outils dans la même réponse (ex: lire src/auth.ts à l'index: 0 et lire tests/auth.test.ts à l'index: 1). Le champ index permet à l'accumulateur SSE d'OpenCode et de Cursor de ranger chaque fragment de JSON dans le bon tampon mémoire (buffer[0], buffer[1]) sans mélanger les arguments des différents outils !

5. Comparaison Architecturale : Gestion des Tool Calls & du Streaming dans OpenCode vs Cursor

Mécanisme Runtime OpenCode (TUI / Desktop / CLI) Cursor (Agent Mode / Composer)
Cycle de vie interne d'un tool_call Modélisé comme une entité ToolPart qui transite par 4 états persistés localement : pending (accumulation SSE) → running (outil en cours) → completed ou error. Affiché sous forme de carte d'action en direct dans le panneau Agent (lecture, recherche ou prévisualisation de diff via le modèle Fast Apply).
Validation des arguments après JSON.parse() Validation stricte au runtime via le schéma Zod de l'outil avant toute invocation ; en cas d'échec, l'erreur de validation est renvoyée au LLM. Validation par le moteur interne de l'IDE et application des filtres .cursorignore / .cursor/cli.json avant l'accès au fichier.
Exécution parallèle (parallel_tool_calls) Les appels de lecture (read, grep, glob) reçus dans un même tour (index: 0, 1...) sont résolus concurremment via Promise.all(). Les lectures et recherches multi-fichiers sont parallélisées, tandis que les commandes shell ou éditions conflictuelles sont sérialisées.
