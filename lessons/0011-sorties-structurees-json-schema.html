Garantir le Contrat de Sortie : Structured Outputs (json_schema & strict: true)

Comment transformer la sortie finale d'un agent IA en un payload JSON mathématiquement garanti, directement consommable par un parseur jq, un microservice ou un pipeline CI/CD sans risque de crash ?

📖 Fil Rouge Architectural • Chapitre 11
Dans les Actes I à III (Étapes 1 à 10), notre agent a appris à dialoguer avec un humain. Mais nous entrons maintenant dans l'Acte IV : l'intégration machine-à-machine (Headless Automation). Nous voulons qu'un script automatisé interroge le modèle pour auditer un diff Git et bloque le déploiement si un bug critique est détecté. Le hic ? Un LLM adore répondre « Bien sûr ! Voici le JSON demandé : ```json ... ``` », ce qui fait immédiatement planter JSON.parse() ou jq !
🔴 Le Problème Technique : Hallucinations Syntaxiques & Clés Manquantes
Demander « Réponds uniquement en JSON valide » dans le prompt système (ou utiliser l'ancien mode {"type": "json_object"}) ne garantit pas le respect du schéma : le modèle peut omettre un champ obligatoire, inventer une clé mal orthographiée (severite au lieu de severity) ou passer une chaîne au lieu d'un booléen.
🟢 La Solution Architecturale : Le Décodage Contraint (Constrained Decoding)
Avec response_format: { "type": "json_schema", "json_schema": { "strict": true, ... } }, le serveur d'inférence compile votre JSON Schema en une grammaire hors-contexte (Context-Free Grammar / Automate à états finis). À chaque étape de génération, les logits des tokens qui violeraient le schéma sont masqués à $-\infty$ (probabilité $0$). Il devient mathématiquement impossible pour le modèle de produire un JSON non conforme.

2. Requête cURL Complète avec strict: true

Pour que le compilateur de grammaire d'OpenAI accepte votre schéma en mode "strict": true, trois règles structurelles doivent être respectées sur chaque objet du schéma :

  1. "strict": true doit être activé à la racine de json_schema.
  2. "additionalProperties": false doit être défini sur chaque type: "object" (interdit toute clé inventée).
  3. Le tableau "required": [...] doit lister explicitement toutes les clés déclarées dans properties.
curl https://api.openai.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "model": "gpt-4o-mini",
    "temperature": 0.0,
    "messages": [
      {
        "role": "system",
        "content": "Tu es un auditeur de sécurité DevSecOps. Analyse le diff fourni."
      },
      {
        "role": "user",
        "content": "+ const query = \"SELECT * FROM users WHERE id = \" + req.query.id;"
      }
    ],
    "response_format": {
      "type": "json_schema",
      "json_schema": {
        "name": "security_audit_verdict",
        "strict": true,
        "schema": {
          "type": "object",
          "properties": {
            "blocking": {
              "type": "boolean",
              "description": "True si une faille critique interdit la fusion de la branche."
            },
            "severity": {
              "type": "string",
              "enum": ["LOW", "MEDIUM", "HIGH", "CRITICAL"]
            },
            "vulnerability_type": {
              "type": "string"
            },
            "remediation": {
              "type": "string"
            }
          },
          "required": ["blocking", "severity", "vulnerability_type", "remediation"],
          "additionalProperties": false
        }
      }
    }
  }'
