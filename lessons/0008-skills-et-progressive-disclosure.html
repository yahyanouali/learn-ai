Savoir-Faire Métier & Workflows à la Demande : Skills (SKILL.md) & Commandes Slash (/commands)

Pourquoi ne faut-il jamais copier 40 procédures opérationnelles dans AGENTS.md ? Découvrez le pattern de Divulgation Progressive (Progressive Disclosure) avec les Skills, ainsi que l'automatisation des prompts récurrents avec les Commandes Slash (.opencode/commands/*.md & .cursor/commands/*.md).

📖 Fil Rouge Architectural • Chapitre 8
À l'Étape 7, nous avons placé nos règles globales dans AGENTS.md. Très vite, toute l'entreprise veut y ajouter ses procédures spécialisées : comment migrer une base Prisma, comment auditer un contrat Solidity, comment déployer sur Kubernetes, comment rédiger un post-mortem... Notre AGENTS.md atteint 55 000 tokens ! Il dépasse le budget, dilue l'attention du modèle (phénomène de Lost in the Middle) et ralentit chaque question triviale.
🔴 Le Problème Technique : Surcharge Cognitive & Dilution d'Attention
Les Rules (AGENTS.md) sont conçues pour des contraintes permanentes et courtes. Si vous y injectez 30 guides procéduraux de 1 500 tokens chacun, 97% de ces instructions sont totalement hors-sujet pour la tâche courante, mais occupent la Context Window et dégradent la précision d'attention du Transformer.
🟢 La Solution Architecturale : Les Skills & Progressive Disclosure
Un Skill est un dossier modulaire (SKILL.md + scripts/ + references/). Au démarrage, l'agent applique le pattern de Progressive Disclosure (chargement paresseux en 3 niveaux) :
1. Niveau 1 (Indexation) : Seuls name + description (~25 tokens) sont listés dans le catalogue de l'outil skill.
2. Niveau 2 (Activation) : Si la tâche correspond, le LLM appelle l'outil skill(name) qui charge le corps de SKILL.md dans role: "tool".
3. Niveau 3 (Exécution) : Le LLM n'exécute les scripts de scripts/ ou ne lit references/ qu'en cas de besoin.

1. Anatomie Standardisée d'un Skill (Standard Agent Skills)

Le format Agent Skills est un standard ouvert supporté nativement à la fois par OpenCode, Cursor et Claude Code. Un skill est un répertoire portant le nom de la compétence (en kebab-case) et contenant obligatoirement un fichier SKILL.md : 

.agents/skills/prisma-migration-safe/
├── SKILL.md                        # Frontmatter YAML (name, description) + Runbook Markdown
├── scripts/
│   └── check-destructive-sql.sh    # Script exécutable vérifiant les DROP TABLE / COLUMN
└── references/
    └── zero-downtime-patterns.md   # Documentation approfondie lue uniquement si nécessaire

Code Source de SKILL.md

---
name: prisma-migration-safe
description: >-
  Génère et vérifie une migration SQL Prisma sans interruption de service (Zero-Downtime).
  À utiliser dès que l'utilisateur modifie schema.prisma ou demande une migration de base de données.
---

# Procédure de Migration Prisma Zero-Downtime

Lorsque tu dois créer ou valider une migration de base de données :
1. Génère le fichier SQL en mode brouillon sans l'appliquer :
   `bunx prisma migrate diff --from-schema-datamodel prisma/schema.prisma --script > /tmp/draft.sql`
2. Exécute le script de vérification : `./scripts/check-destructive-sql.sh /tmp/draft.sql`.
3. Si une opération destructive (`DROP COLUMN`, `ALTER COLUMN TYPE`) est détectée, consulte obligatoirement le guide `./references/zero-downtime-patterns.md` (Pattern Expand & Contract).

4. Les Commandes Slash Personnalisées (Commands) dans OpenCode & Cursor

Si les Skills (SKILL.md) permettent à l'agent de charger un savoir-faire métier de manière autonome lorsqu'il en détecte le besoin, comment créer un raccourci de prompt paramétré déclenché explicitement par le développeur (par exemple /review src/auth.ts, /commit ou /audit) ? C'est le rôle exact des Commandes Slash (Commands) documentées sur opencode.ai/docs/commands/ et dans Cursor.

🔴 Le Problème : La Répétition Manuelle des Prompts Quotidiens
Vingt fois par jour, les membres de votre équipe tapent des consignes récurrentes : « Lance git diff --cached, vérifie les failles de sécurité, passe le mode Plan avec Claude Sonnet et propose un message de commit conventionnel... ». Retaper ce prompt à la main est lent, sujet aux oublis et oblige sinon l'agent à faire un aller-retour d'outil (tool_call: bash) rien que pour lire le git diff.
🟢 La Solution : Les Custom Slash Commands (/commande)
Une Commande est un template Markdown (dans .opencode/commands/*.md ou .cursor/commands/*.md) ou JSON (dans opencode.jsonc). Dès que vous tapez /review src/auth.ts, le client évalue les arguments ($ARGUMENTS, $1, $2), exécute localement les éventuels blocs shell (!`git diff`) avant l'appel HTTP, bascule sur l'agent/modèle configuré et soumet le résultat directement comme message "role": "user" !

Déclarer une Commande dans OpenCode : Fichier Markdown vs opencode.jsonc

Dans OpenCode, les commandes Markdown et JSON partagent un registre unique (les fichiers sont rechargés à chaud sans redémarrer OpenCode, et une commande projet écrase une commande globale ou intégrée du même nom) :

  • Commandes Projet (partagées via Git, prioritaires) : .opencode/commands/<nom>.md
  • Commandes Globales Utilisateur : ~/.config/opencode/commands/<nom>.md
  • Sous-dossiers (Namespaces) : Un fichier placé dans .opencode/commands/team/review.md crée automatiquement la commande /team/review ! (Note : l'ancien dossier au singulier command/ reste reconnu par rétrocompatibilité, mais utilisez commands/ pour tout nouveau fichier).
📄 Méthode 1 : Fichier .opencode/commands/review.md
---
description: Revue de code complète (bugs et tests manquants)
agent: plan
model: anthropic/claude-sonnet-4-5#high
subagent: false
---

Analyse attentivement $ARGUMENTS.
Signale d'abord les bugs critiques et les failles de sécurité,
puis vérifie la couverture des tests unitaires.
⚙️ Méthode 2 : Clé "commands" (ou alias "command") dans opencode.jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "commands": {
    "review": {
      "description": "Revue de code complète (bugs et tests manquants)",
      "template": "Analyse attentivement $ARGUMENTS. Signale d'abord les bugs critiques.",
      "agent": "plan",
      "model": "anthropic/claude-sonnet-4-5#high",
      "subagent": false
    },
    "audit": {
      "description": "Audit d'un package en arrière-plan",
      "template": "Audite le package $ARGUMENTS.",
      "agent": "general",
      "subagent": true
    }
  }
}

Référence des Champs de Configuration d'une Commande OpenCode

Champ Requis ? Comportement & Règles de Priorité (Documentation Officielle OpenCode)
template JSON uniquement Le corps du prompt à envoyer. (En Markdown, ne mettez jamais template dans le frontmatter YAML : c'est le corps du fichier .md qui sert de template).
description Optionnel Texte d'aide affiché dans le menu d'autocomplétion lorsque vous tapez / dans le TUI.
agent Optionnel Bascule sur l'agent indiqué au lancement de la commande (ex: plan, build, general ou un agent personnalisé).
model Optionnel Surcharge le modèle au format provider/model ou provider/model#variant. Priorité : 1. model de la commande → 2. model de l'agent cible → 3. model de la session active.
subagent Optionnel Booléen : true lance la commande dans une session enfant isolée en arrière-plan (même si l'agent a mode: primary) ; false force la session courante (même si l'agent a mode: subagent) ; omis = suit le mode de l'agent.
subtask Optionnel Alias historique déprécié de subagent. Si subagent et subtask sont tous deux présents, subagent l'emporte toujours.

5. Les Placeholders Dynamiques d'OpenCode : $ARGUMENTS, $1, !`shell` et @fichier

Toute la puissance des commandes OpenCode réside dans leur moteur de pré-évaluation locale avant l'envoi de la requête HTTP au LLM :

🔤 1. Arguments ($ARGUMENTS, $1, $2 & Fallback)
  • $ARGUMENTS : Insère la chaîne complète telle que saisie (ex: /component Account Settings → Account Settings).
  • Positionnels ($1, $2, $3...) : Découpe par espaces ; les guillemets groupent les mots et sont retirés (ex: /check src/auth.ts "error handling" → $1 = src/auth.ts, $2 = error handling). Le numéro le plus élevé absorbe son argument et tout ce qui suit.
  • Fallback automatique : Si le template ne contient aucun placeholder (ni $ARGUMENTS ni $1), OpenCode ajoute les arguments saisis après une ligne vide à la fin du prompt !
⚡ 2. Injection Shell (!`cmd`) & Fichiers (@path)
  • Sortie Shell !`commande` : Exécute la commande dans le shell local du projet et injecte stdout/stderr directement dans le prompt avant l'envoi au LLM ! Les placeholders ($1) sont expansés avant l'exécution du shell.
  • Références @fichier & Pièces jointes : Dans un template stocké, @README.md reste du texte indicatif, mais tout fichier attaché via @src/auth.ts dans le compositeur lors de l'invocation de /review @src/auth.ts est préservé et joint au prompt envoyé au LLM.
# Exemple 1 : .opencode/commands/review-diff.md (Injection Shell directe)
---
description: Analyse les modifications Git indexées avant commit
agent: plan
---
Voici le résumé et le diff exact des fichiers stagés :

!`git diff --cached --stat && git diff --cached`

Vérifie ce diff pour détecter toute régression ou secret oublié.

# Exemple 2 : .opencode/commands/history.md (Combinaison $1 + Shell !`...`)
---
description: Résume les N derniers commits Git (ex: /history 5)
---
Résume de manière synthétique ces $1 derniers commits :

!`git log --oneline -$1`
⚠️ Avertissement de Sécurité sur les Blocs Shell (!`commande`) :
Les blocs !`...` sont évalués localement par OpenCode au moment où vous lancez la commande, en dehors du flux de permissions d'outils (permission.bash) de l'agent. N'utilisez que des commandes provenant de dépôts de confiance et n'insérez jamais d'arguments non fiables dans un bloc !`...`$1`.

6. Comparaison des Commandes Slash : OpenCode vs Cursor (.cursor/commands/*.md)

Cursor supporte également les commandes slash personnalisées basées sur des fichiers Markdown :

⚡ OpenCode : .opencode/commands/pr-check.md
---
description: Vérifie la branche courante avant ouverture de PR
agent: plan
model: anthropic/claude-sonnet-4-5#high
---

Cible de la revue : $ARGUMENTS

Diff par rapport à main :
!`git diff main...HEAD --stat`

Vérifie les conventions de @AGENTS.md et liste les risques.
🖱️ Cursor : .cursor/commands/pr-check.md
# Vérification avant Pull Request

1. Analyse les modifications de la branche courante et les fichiers attachés.
2. Vérifie l'absence de `console.log`, de types `any` et de secrets exposés.
3. Propose un titre et une description de Pull Request structurée.

# Invocation dans le chat Cursor :
# /pr-check @src/auth.ts
Caractéristique OpenCode (opencode.ai/docs/commands/) Cursor (Custom Slash Commands)
Emplacements des fichiers • Projet : .opencode/commands/*.md
• Global : ~/.config/opencode/commands/*.md
• Config : clé "commands" dans opencode.jsonc		 • Projet : .cursor/commands/*.md (partagé via Git)
• Global : ~/.cursor/commands/*.md
Interpolation d'arguments $ARGUMENTS, positionnels $1, $2, $3 (avec gestion des guillemets) et fallback automatique en fin de prompt. Texte et tags de contexte (ex: /refactor @src/utils.ts) ajoutés à la suite de la commande dans la boîte de saisie.
Injection Shell pré-requête Support natif via la syntaxe !`commande` évaluée localement avant l'envoi HTTP. Pas d'évaluation shell dans le template : l'agent appelle son outil terminal pendant la boucle ReAct si nécessaire.
Contrôle d'exécution (Frontmatter) Frontmatter YAML : description, agent, model, subagent: true/false (et alias subtask). Fichier Markdown pur exécuté dans le mode et avec le modèle actuellement sélectionnés dans le panneau Cursor.

7. La Matrice de Décision Architecturale : Rules vs Commands vs Skills vs Subagents

Vous maîtrisez désormais les briques de personnalisation de l'Acte III. Voici comment choisir immédiatement la bonne abstraction selon votre besoin :

Brique Architecturale Qui déclenche ? Fichiers (OpenCode / Cursor) Injection dans /v1/chat/completions Cas d'Usage Idéal
1. Rules
(Étape 7)		 Automatique
(Toujours actif ou par glob de fichier)		 AGENTS.md, instructions[]
.cursor/rules/*.mdc		 Inliné dès le Tour 1 dans role: "system" (messages[0]). Standards de code permanents, stack technique (« Utilise Bun et Zod, jamais any »).
2. Commands
(Étape 8)		 Le Développeur
(Manuellement via /commande)		 .opencode/commands/*.md
.cursor/commands/*.md		 Template expansé ($1, !`shell`) envoyé comme role: "user". Raccourcis de workflows quotidiens déclenchés à la demande (/review-diff, /commit, /pr-check).
3. Skills
(Étape 8)		 L'Agent (LLM)
(À la demande via l'outil skill ou /skill)		 .agents/skills/<nom>/SKILL.md
.opencode/skills/, .cursor/skills/		 Catalogue (~25 tok) au départ ; corps complet chargé dans role: "tool" (Progressive Disclosure). Runbooks métiers lourds avec scripts (migrations SQL Zero-Downtime, déploiement K8s, audit).
4. Subagents
(Étape 9)		 L'Agent ou le Dev
(Outil task, @agent ou commande subagent: true)		 .opencode/agents/*.md
.cursor/agents/*.md		 Session enfant avec son propre messages[] isolé ; seule la synthèse revient dans role: "tool". Exploration massive de code ou audit en lecture seule sans polluer la Context Window principale.
