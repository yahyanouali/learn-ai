Standardiser les Outils Externes : Le Model Context Protocol (MCP) & Handshake JSON-RPC

Comment connecter GitHub, Playwright, PostgreSQL ou Neo4j à OpenCode et Cursor sans jamais modifier le code source de l'agent ? Étude au niveau protocole de la norme MCP.

📖 Fil Rouge Architectural • Chapitre 5
Dans l'Acte I (Étapes 1 à 4), nous avons construit une boucle agentique complète autour des outils natifs (read, edit, bash). Mais en entreprise, un ingénieur doit interagir avec des dizaines de systèmes tiers : GitHub, Jira, Playwright, bases de données graphe (Graphiti/Neo4j), Sentry... Faut-il recompiler OpenCode ou Cursor pour chaque nouveau connecteur ?
🔴 Le Problème Technique : Le Problème M × N
Si chaque éditeur IA (OpenCode, Cursor, Claude Code, Windsurf — M clients) devait coder en dur des connecteurs spécifiques pour chaque service (GitHub, Postgres, Slack, Figma — N services), l'industrie devrait maintenir M × N intégrations propriétaires incompatibles entre elles.
🟢 La Solution Architecturale : Le Protocole MCP
À l'image du LSP (Language Server Protocol) qui a standardisé les analyseurs de code dans les IDE, le Model Context Protocol (MCP) découple l'agent (MCP Host/Client) des fournisseurs d'outils (MCP Servers) via un protocole universel basé sur JSON-RPC 2.0 (sur flux stdio local ou Streamable HTTP distant).

1. Les 4 Phases du Cycle de Vie MCP (Handshake & Découverte)

Lorsqu'OpenCode ou Cursor démarre, il lit sa configuration MCP, instancie chaque serveur local en tant que sous-processus enfant (via npx, uvx ou docker run -i) et exécute un handshake JSON-RPC 2.0 en 3 étapes avant de pouvoir convertir les outils MCP au format OpenAI tools[] :

Phase A : Négociation des Capacités (initialize)

// 1. Requête envoyée par OpenCode/Cursor sur le STDIN du serveur MCP
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-03-26",
    "capabilities": {
      "roots": { "listChanged": true },
      "sampling": {}
    },
    "clientInfo": { "name": "opencode", "version": "1.14.49" }
  }
}

// 2. Réponse du serveur MCP sur son STDOUT (versions courantes : "2025-03-26" / "2024-11-05")
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-03-26",
    "capabilities": {
      "tools": { "listChanged": true },
      "resources": {}
    },
    "serverInfo": { "name": "github-mcp-server", "version": "1.0.0" }
  }
}

Que signifient exactement ces objets capabilities échangés au démarrage ?

Lors du handshake initialize, le client (OpenCode / Cursor) et le serveur MCP ne savent pas encore quelles briques du protocole l'autre supporte. Ils s'annoncent mutuellement leurs capacités (capabilities) :

💻 1. Capacités annoncées par le CLIENT (OpenCode / Cursor)
  • "roots": { "listChanged": true } (Dossiers racines autorisés) :
    Le client indique qu'il peut fournir au serveur MCP la liste des dossiers du projet ouverts par l'utilisateur (ex: file:///c:/Projects/mon-app via roots/list) pour délimiter son périmètre d'action.
    • Que signifie "listChanged": true ? Le client promet d'envoyer une notification (notifications/roots/list_changed) si l'utilisateur ajoute ou retire un dossier de son espace de travail en cours de session.
  • "sampling": {} (Délégation d'appel LLM au client) :
    Un serveur MCP ne possède pas de clé API OpenAI/Anthropic. En déclarant sampling: {}, l'agent (OpenCode/Cursor) dit au serveur MCP : « Si tu as besoin de faire résumer ou analyser un texte par le LLM pendant ton travail, envoie-moi une requête sampling/createMessage et je ferai l'appel LLM pour toi avec la connexion de l'utilisateur. »
🔌 2. Capacités annoncées par le SERVEUR MCP (ex: GitHub, Postgres)
  • "tools": { "listChanged": true } (Catalogue d'outils) :
    Le serveur annonce qu'il expose des fonctions exécutables par le LLM (que l'agent va immédiatement récupérer via tools/list pour les injecter dans le tableau tools[] d'OpenAI vu à l'Étape 2).
    • Que signifie "listChanged": true ? Le serveur prévient que sa liste d'outils peut changer dynamiquement en cours de route : s'il active un nouvel outil, il enverra notifications/tools/list_changed pour que l'agent rafraîchisse son catalogue sans redémarrer !
  • "resources": {} (Données consultables en lecture seule) :
    Contrairement aux tools (qui exécutent une action), les resources sont des données passives identifiées par une adresse URI (ex: postgres://db/schema, github://issues/42) que l'agent peut lire directement via resources/read (comme un fichier attaché avec @ dans le chat).
    (Note : un serveur MCP peut aussi annoncer "prompts": {} s'il fournit des modèles de commandes slash / pré-formatés).

Phase B : Confirmation (notifications/initialized) & Découverte (tools/list)

// 3. Notification (sans "id") confirmant que le client est prêt
{ "jsonrpc": "2.0", "method": "notifications/initialized" }

// 4. Découverte du catalogue d'outils exposés par le serveur MCP
{ "jsonrpc": "2.0", "id": 2, "method": "tools/list", "params": {} }

// 5. Le serveur MCP renvoie ses outils avec leur JSON Schema (inputSchema)
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "tools": [
      {
        "name": "get_pull_request",
        "description": "Get details of a specific pull request",
        "inputSchema": {
          "type": "object",
          "properties": {
            "owner": { "type": "string" },
            "repo": { "type": "string" },
            "pullNumber": { "type": "number" }
          },
          "required": ["owner", "repo", "pullNumber"]
        }
      }
    ]
  }
}

Phase C : Traduction automatique (Pont MCP → OpenAI) et Exécution (tools/call)

OpenCode/Cursor préfixe le nom de l'outil avec le nom du serveur (ex: github-mcp-server_get_pull_request pour éviter toute collision de noms), copie son inputSchema dans le champ parameters du tableau tools[] OpenAI (Étape 2), et lorsque le LLM émet un tool_call (Étape 3), l'agent le traduit en requête JSON-RPC tools/call : 

// 6. Appel d'outil envoyé au serveur MCP suite à un tool_call du LLM
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "get_pull_request",
    "arguments": { "owner": "anomalyco", "repo": "opencode", "pullNumber": 42 }
  }
}

// 7. Réponse du serveur MCP : le tableau "content" est ensuite injecté dans role: "tool" (Étape 4)
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "PR #42: Fix token refresh race condition in src/auth.ts (+18 -4)"
      }
    ],
    "isError": false
  }
}

3. Configuration Officielle Comparée : OpenCode vs Cursor

Bien que le protocole sous-jacent soit 100% identique, la syntaxe du fichier de configuration diffère légèrement entre OpenCode et Cursor :

Caractéristique OpenCode (~/.config/opencode/opencode.jsonc ou opencode.json) Cursor (.cursor/mcp.json ou ~/.cursor/mcp.json)
Clé racine JSON "mcp": { ... } "mcpServers": { ... }
Déclaration d'un serveur local (stdio) "type": "local" avec un tableau unique "command": ["npx", "-y", "..."] et "environment": { ... }. Chaîne "command": "npx" séparée du tableau "args": ["-y", "..."] et "env": { ... }.
Déclaration d'un serveur distant (HTTP/SSE) "type": "remote" avec "url": "https://..." et "headers": { ... }. "url": "https://.../mcp" (Streamable HTTP ou SSE).
⚙️ Exemple Réel OpenCode (opencode.jsonc)
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "playwright-firefox": {
      "type": "local",
      "command": [
        "npx", "-y", "@playwright/mcp@latest", "--browser=firefox"
      ]
    },
    "memory": {
      "type": "local",
      "command": [
        "npx", "-y", "@modelcontextprotocol/server-memory"
      ],
      "environment": {
        "MEMORY_FILE_PATH": "C:\\Users\\Dev\\.agents\\memory.json"
      }
    }
  }
}
⚙️ Équivalent Exact Cursor (.cursor/mcp.json)
{
  "mcpServers": {
    "playwright-firefox": {
      "command": "npx",
      "args": [
        "-y", "@playwright/mcp@latest", "--browser=firefox"
      ]
    },
    "memory": {
      "command": "npx",
      "args": [
        "-y", "@modelcontextprotocol/server-memory"
      ],
      "env": {
        "MEMORY_FILE_PATH": "C:\\Users\\Dev\\.agents\\memory.json"
      }
    }
  }
}
