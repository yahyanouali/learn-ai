Passer à l'Échelle : Le "Code Mode" et l'Outil execute (Situation A vs Situation B)

Que se passe-t-il lorsque vous connectez 10 serveurs MCP totalisant 120 outils ? Découvrez comment le paradigme Code Mode (CodeAct) remplace 15 allers-retours HTTP JSON par l'exécution locale d'un script TypeScript/JavaScript unique.

📖 Fil Rouge Architectural • Chapitre 6
À l'Étape 5, enthousiasmés par la simplicité de MCP, nous avons branché dans opencode.jsonc dix serveurs MCP : GitHub (35 outils), Playwright (25 outils), Jira, Filesystem, Memory, Graphiti... Soudain, chaque requête vers le LLM devient lente et coûte 40 000 tokens avant même d'avoir commencé à travailler ! Pourquoi le Tool Calling unitaire (Étapes 2 à 4) montre-t-il ses limites à grande échelle ?
🔴 Le Problème Technique : Explosion du Contexte & Latence Séquentielle
Avec le Tool Calling classique (Situation A : "codeMode": false) :
1. Bloat de schémas : Sérialiser 120 JSON Schemas complets dans tools[] consomme 25 000 à 40 000 tokens dès le premier message.
2. Allers-retours N+1 : Pour lister 10 tickets Jira et commenter 10 PR GitHub, le LLM doit faire 20 tours de boucle HTTP séquentiels, ré-ingérant tous les JSON intermédiaires dans sa Context Window.
🟢 La Solution Architecturale : Le "Code Mode" (CodeAct)
En activant le Code Mode (Situation B : "codeMode": true), l'agent expose les signatures compactes des outils sous forme d'API TypeScript dans le prompt système, et ne déclare qu'un seul méta-outil dans tools[] : execute. Le LLM écrit un script JS/TS asynchrone avec boucles for, filtres et conditions if, exécuté localement dans une sandbox (@opencode/codemode) en 1 seul aller-retour HTTP (-85% de tokens).
Distinction Architecturale Importante — Où s'exécute le Code Mode ?
Le Code Mode (popularisé par l'architecture CodeAct, Cloudflare MCP Code Mode et @opencode/codemode) est un mécanisme côté client (Runtime Agent) et non un paramètre natif des serveurs d'OpenAI. C'est votre agent local qui choisit, avant d'envoyer la requête HTTP vers /v1/chat/completions, soit d'injecter les 120 JSON Schemas dans tools[] (Situation A), soit de les remplacer par des signatures TypeScript compactes dans role: "system" et un unique méta-outil execute dans tools[] (Situation B).

1. Comparaison Réseau Exacte : Situation A (Classique) vs Situation B (Code Mode)

Prenons une tâche réelle : « Récupère les tickets Jira assignés à Alice et crée un commentaire récapitulatif sur la Pull Request #42 uniquement pour les tickets bloquants. »

Conséquence : Le LLM appelle jira_search_issues (Tour 1), reçoit 500 lignes de JSON brut (Tour 2), appelle 5 fois jira_get_issue_details (Tours 3 à 7), puis appelle github_create_pr_comment (Tour 8).

Situation B : "codeMode": true (Méta-Outil execute)
{
  "messages": [
    {
      "role": "system",
      "content": "Tu es OpenCode en Code Mode.\nAPI disponible dans l'outil execute :\ndeclare namespace tools {\n  function jira_search_issues(args: { assignee: string }): Promise;\n  function github_create_pr_comment(args: { pr: number, body: string }): Promise;\n}"
    },
    {
      "role": "user",
      "content": "Commente la PR #42 avec les tickets bloquants d'Alice."
    }
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "execute",
        "description": "Exécute un script JS async orchestrant l'API tools.*",
        "parameters": {
          "type": "object",
          "properties": {
            "code": { "type": "string" }
          },
          "required": ["code"]
        }
      }
    }
  ]
}

Conséquence : Le LLM émet 1 seul tool_call vers execute contenant un script JS qui filtre les données en mémoire locale et ne renvoie au LLM qu'un résumé de 2 lignes !

2. Ce que génère le LLM en Situation B (Payload de execute)

Lorsque le Code Mode est actif, voici le tool_call unique émis par l'assistant et exécuté dans la sandbox locale d'OpenCode : 

// Script généré par le LLM dans l'argument "code" de l'outil "execute"
const issues = await tools.jira_search_issues({ assignee: "alice" });

// Le filtrage s'exécute à vitesse CPU locale sans repasser par la Context Window du LLM !
const blockers = issues.filter(issue => issue.priority === "Blocker" && issue.status !== "Done");

if (blockers.length > 0) {
  const markdownList = blockers.map(b => `- **${b.key}** : ${b.summary}`).join("\n");
  await tools.github_create_pr_comment({
    pr: 42,
    body: `### ⚠️ Tickets Bloquants d'Alice (${blockers.length})\n${markdownList}`
  });
}

// Seule cette valeur de retour distillée sera injectée dans role: "tool" !
return `Succès : ${blockers.length} tickets bloquants publiés sur la PR #42.`;

4. Matrice de Décision : Quand activer ou désactiver le Code Mode ?

Critère d'Ingénierie Situation A : Tool Calling Classique ("codeMode": false) Situation B : Code Mode Activé ("codeMode": true)
Nombre de serveurs MCP actifs Idéal pour 1 à 3 serveurs (< 25 outils). Indispensable au-delà de 30+ outils MCP connectés simultanément.
Nature du workflow Appels unitaires simples (lire un fichier, éditer une fonction). Pipelines de données multi-étapes (boucles, jointures entre 2 APIs, agrégations).
Consommation de Tokens Élevée (tous les JSON intermédiaires polluent l'historique messages[]). Réduite jusqu'à 85% (les payloads intermédiaires meurent dans la sandbox JS).
Contrôle granulaire (Permissions / Hooks) Intercepté directement appel par appel à la frontière du runtime. Le proxy RPC de la sandbox vérifie chaque sous-appel tools.* contre les permissions d'OpenCode.
Implémentation dans OpenCode vs Cursor Mode par défaut dans OpenCode et Cursor (chaque outil MCP actif est sérialisé dans tools[], avec possibilité dans Cursor de désactiver certains outils MCP dans l'interface). Dans OpenCode via l'intégration @opencode/codemode (méta-outil execute en sandbox JS) ; dans Cursor via la découverte dynamique d'outils MCP à la demande et l'exécution de scripts d'orchestration dans la sandbox terminal.
