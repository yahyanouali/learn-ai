Programmer la Boucle Agentique : Plugins OpenCode (V2 & V1) & Hooks Cursor

Les Rules (Étape 7) et les Skills (Étape 8) ne sont que du texte Markdown que le LLM peut parfois ignorer. Voyons comment brancher du vrai code TypeScript/JavaScript au cœur du moteur de l'agent pour contrôler ses requêtes HTTP et ses outils à 100%.

📖 Fil Rouge Architectural • Chapitre 10
Jusqu'ici, nous avons guidé le LLM avec du texte Markdown (AGENTS.md, SKILL.md). Mais que se passe-t-il si un outil lit un fichier contenant par erreur un mot de passe ou une clé API sk-live-... ? Avant même que le LLM ne puisse lire une consigne lui disant « ignore ce secret », la clé a déjà quitté votre machine dans le message HTTP role: "tool" (Étape 4) ! Pour garantir la sécurité, il nous faut du code déterministe qui s'exécute avant et après les outils ainsi qu'à la frontière HTTP du LLM.
🔴 Le Problème : Le Markdown est Probabiliste
Écrire « N'exécute jamais rm -rf et ne lis jamais les secrets » dans AGENTS.md est un conseil donné au LLM, pas une barrière technique. Si le modèle hallucine ou subit une attaque par Prompt Injection, il peut violer la consigne.
🟢 La Solution : Les Plugins & Hooks Déterministes
OpenCode permet de charger des fichiers .ts / .js dans .opencode/plugins/ ou ~/.config/opencode/plugins/ (et Cursor utilise .cursor/hooks.json). Ce code s'intercale physiquement dans le moteur de l'agent pour inspecter, modifier ou bloquer les appels d'outils et les requêtes HTTP avec une garantie de 100%.

1. Les Fondations : Comprendre l'Architecture des Plugins OpenCode (V2 vs V1)

Un plugin OpenCode est un fichier TypeScript (.ts) ou JavaScript (.js) exécuté directement par le runtime Bun intégré à OpenCode. Vous pouvez le déposer :

  • Dans .opencode/plugins/ (actif pour le projet courant) ou ~/.config/opencode/plugins/ (actif globalement pour tous vos projets).
  • Ou le déclarer dans opencode.json via la clé "plugin": ["./plugins/mon-plugin.ts"].
Point clé avant de lire du code : OpenCode V1 vs OpenCode V2
En parcourant la documentation ou des plugins existants (comme openintercept.ts et openintercept-v2.ts), vous rencontrerez deux générations d'API de plugins :
  • L'Architecture V2 (OpenCode 2.x / Desktop — @opencode/plugin) : Le standard actuel. Le plugin exporte un objet { id, setup(ctx) } (souvent via Plugin.define(...)) et enregistre ses hooks de manière impérative sur les domaines de ctx : await ctx.tool.hook(...), await ctx.session.hook(...) et await ctx.tool.transform(...).
  • L'Architecture V1 (OpenCode 1.x CLI historique — @opencode-ai/plugin) : Le plugin exporte une simple fonction async (ctx) => ({ ... }) qui retourne un objet statique de hooks ("tool.execute.before", "tool.execute.after", tool: { ... }).

🚀 Architecture OpenCode V2 (2.x / Desktop — Recommandée)
// Package V2 : @opencode/plugin
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  // 1. Identifiant unique du plugin
  id: "mon-org.mon-plugin",

  // 2. Fonction setup(ctx) appelée à l'activation du workspace
  async setup(ctx) {
    // Domaines exposés par ctx en V2 :
    // - ctx.tool.hook("execute.before" | "execute.after", fn)
    // - ctx.tool.transform(editor => ...)
    // - ctx.session.hook("model.request" | "http.request" | "http.response", fn)

    await ctx.tool.hook("execute.before", async (event) => {
      // event contient { id, tool, sessionID, agent, input }
    })

    // 3. Optionnel : retourne une fonction de nettoyage (cleanup)
    // appelée quand le projet/workspace est fermé ou rechargé
    return async () => {
      // Nettoyage des timers ou de l'état local
    }
  }
})
📦 Architecture OpenCode V1 (1.x CLI Historique)
// Package V1 : @opencode-ai/plugin
import { type Plugin } from "@opencode-ai/plugin"

// 1. Fonction asynchrone recevant { client, directory, $ }
export const MonPluginV1: Plugin = async (ctx) => {

  // 2. Retourne un dictionnaire statique de hooks
  //    Chaque hook reçoit DEUX paramètres : (input, output)
  return {
    "tool.execute.before": async (input, output) => {
      // input  = { tool, sessionID, callID }
      // output = { args } (arguments de l'outil)
    },

    "tool.execute.after": async (input, output) => {
      // output = { title, output, metadata }
    }
  }
}

export default MonPluginV1

B. Vue d'Ensemble : Où se branchent les Hooks V2 dans la Boucle Agentique ?

En OpenCode V2, l'objet ctx passé à setup(ctx) est organisé en deux grands domaines qui couvrent toute la boucle agentique (Étapes 1 à 4) :

  • ctx.session : Tout ce qui touche à la conversation et aux requêtes HTTP vers le LLM (sélection du modèle, requête HTTP brute Request, réponse HTTP brute Response).
  • ctx.tool : Tout ce qui touche aux outils locaux et MCP (interception avant exécution, interception après exécution, ou transformation/encapsulation d'un outil existant).

2. Les 3 Règles d'Or d'OpenCode V2 (Ce qu'il faut absolument comprendre)

Pour comprendre un vrai plugin de production en OpenCode V2 sans être perdu, il faut connaître 3 comportements internes du moteur :

Règle d'Or n°1 : Les hooks ignorent return — Tout se fait par mutation sur place (replaceInPlace)

Dans OpenCode (V1 comme V2), le moteur ignore la valeur de retour d'un hook execute.before ou execute.after. Il conserve en mémoire la référence vers l'objet original (event.input ou event.result).

  • Si vous modifiez une seule propriété (ex: event.input.url = "https://..."), cela fonctionne directement.
  • Mais si vous voulez remplacer tout l'objet d'arguments d'un coup, écrire event.input = nouveauxArgs ne marchera pas (cela ne fait que changer la propriété locale sans modifier l'objet pointé par le moteur). Il faut vider l'objet existant et copier les nouvelles clés dedans :
// Astuce fondamentale utilisée dans les plugins OpenCode V2 (ex: OpenIntercept) :
// Vide les clés de l'objet existant puis copie les nouvelles clés DANS LA MÊME référence mémoire
function replaceInPlace(target: Record, next: Record) {
  for (const key of Object.keys(target)) {
    delete target[key]
  }
  Object.assign(target, next)
}

Règle d'Or n°2 : En V2, le résultat d'un outil (event.result) a une enveloppe structurée

En V1, la sortie d'un outil dans tool.execute.after était une simple chaîne de caractères (output.output = "texte").
En V2, dans ctx.tool.hook("execute.after", (event) => ...) :

  • event.status indique si l'outil a réussi ("completed") ou échoué ("error").
  • Lorsque event.status === "completed", event.result contient à la fois :
    • event.result.content : Le tableau de blocs de texte que le LLM va réellement lire (ex: [{ type: "text", text: "..." }]).
    • event.result.output : La donnée structurée interne de l'outil (une string pour bash, ou un objet { url, contentType, format, output } pour webfetch).
  • Pour modifier ou nettoyer ce que voit le LLM en V2, on met donc à jour event.result.content = [{ type: "text", text: textePropre }] (ainsi que event.result.output).

Règle d'Or n°3 : Isolation par Workspace dans setup(ctx) et fonction de nettoyage

Dans OpenCode Desktop (V2), si vous ouvrez 3 projets en même temps, OpenCode exécute 3 fois la fonction setup(ctx) de votre plugin global dans le même processus Bun !

  • Ne mettez jamais d'état mutable en variable globale en dehors de setup(ctx), sinon les sessions d'un projet écraseront celles d'un autre.
  • Déclarez votre état (ex: let active = true, new Map()) à l'intérieur de setup(ctx), et retournez une fonction de nettoyage return async () => { active = false } qu'OpenCode appellera automatiquement à la fermeture du projet.

PARTIE 1 • Comprendre par la Pratique : 3 Mini-Plugins V2 de 15 Lignes

Voyons d'abord 3 petits plugins autonomes en OpenCode V2 (chacun illustrant un seul concept), accompagnés de leur impact exact sur le flux HTTP envoyé au LLM.

Exemple 1A : Bloquer la lecture d'un fichier .env avec ctx.tool.hook("execute.before")

📄 Plugin OpenCode V2 (.opencode/plugins/block-env.ts)
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "security.block-env",
  async setup(ctx) {
    // Intercepte chaque outil juste AVANT son exécution
    await ctx.tool.hook("execute.before", async (event) => {
      // event.tool  = nom de l'outil ("read", "bash", etc.)
      // event.input = arguments JSON passés par le LLM
      if (event.tool === "read" && event.input?.filePath?.includes(".env")) {
        // Lever une erreur coupe immédiatement l'exécution !
        throw new Error("Accès refusé : interdiction de lire un fichier .env")
      }
    })
  }
})
📡 Impact sur le Payload HTTP envoyé au LLM (Étape 4)

Le fichier .env n'est jamais ouvert sur le disque. Le moteur OpenCode V2 capture l'erreur et la renvoie au LLM dans role: "tool" : 

{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "Error: Accès refusé : interdiction de lire un fichier .env"
}

Exemple 1B : Inspecter ou enrichir la requête HTTP vers le LLM avec ctx.session.hook("http.request")

En entreprise, une passerelle IA (comme Envoy AI Gateway, LiteLLM ou Azure APIM) exige souvent un en-tête HTTP de traçabilité par session ou par agent. En V2, ctx.session.hook("http.request") vous donne directement accès à l'objet standard Request de l'API Web Fetch :

📄 Plugin OpenCode V2 (.opencode/plugins/trace-headers.ts)
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "corp.trace-headers",
  async setup(ctx) {
    // Appelé juste avant le fetch() d'OpenCode vers le fournisseur LLM
    await ctx.session.hook("http.request", async (ev) => {
      if (!(ev?.request instanceof Request)) return

      // On injecte des en-têtes HTTP de traçabilité sur la requête sortante
      ev.request.headers.set("X-OpenCode-Session", String(ev.sessionID ?? ""))
      ev.request.headers.set("X-OpenCode-Agent", String(ev.agent ?? "main"))
    })
  }
})

Chaque appel HTTP vers /v1/chat/completions ou /v1/responses transporte désormais vos en-têtes d'audit :

Exemple 1C : Encapsuler un outil en V2 (ctx.tool.transform) ou créer un outil avec tool(), Zod et BunShell ($)

En V2 (@opencode/plugin), await ctx.tool.transform(editor => ...) permet d'encapsuler un outil existant, tandis que l'assistant tool() (@opencode-ai/plugin) utilise Zod (tool.schema) et BunShell ($) pour exposer un nouvel outil sur mesure dans tools[] (Étape 2) :

📄 Wrapper V2 (ctx.tool.transform) & Outil tool() (Zod + BunShell)
// A. En V2 (@opencode/plugin) — Encapsuler un outil dans setup(ctx) :
await ctx.tool.transform((editor) => {
  const existing = editor.get("webfetch")
  if (!existing) return
  editor.update("webfetch", (t) => {
    const orig = t.execute.bind(t)
    t.execute = async (args, toolCtx) => orig(args, toolCtx)
  })
})

// B. Avec tool() (@opencode-ai/plugin) — Déclarer un outil typé Zod :
import { type Plugin, tool } from "@opencode-ai/plugin"

export const GitToolPlugin: Plugin = async ({ $ }) => ({
  tool: {
    git_last_commits: tool({
      description: "Récupère les N derniers commits Git du projet",
      args: {
        count: tool.schema.number().int().describe("Nombre de commits")
      },
      async execute(args) {
        return await $`git log -n ${args.count} --oneline`.text()
      }
    })
  }
})

PARTIE 2 • Cas Réel d'Industrialisation en OpenCode V2 : Pare-Feu & DLP d'Entreprise

Passons maintenant à un plugin OpenCode V2 complet et conforme aux spécifications de production (inspiré directement de l'architecture d'openintercept-v2.ts).

Le scénario : Votre agent utilise le serveur MCP GitHub (Étape 5) et un Skill d'audit (Étape 8) pour inspecter des Pull Requests. Votre plugin V2 security-guard-v2.ts applique 4 règles déterministes :

  1. Suivi de session par workspace (ctx.session.hook("model.request")) : Enregistre dans une Map locale à setup(ctx) quel modèle traite quelle session.
  2. Blocage d'outil sensible (ctx.tool.hook("execute.before")) : Interdit à l'agent d'appeler l'outil MCP github-mcp-server_merge_pull_request via throw new Error(...).
  3. Réécriture d'arguments sur place (replaceInPlace dans execute.before) : Si l'agent appelle webfetch avec une URL en http://, le plugin remplace l'URL en https:// via replaceInPlace(event.input, ...).
  4. Purge des secrets avant envoi au LLM (ctx.tool.hook("execute.after")) : Si l'outil a réussi (event.status === "completed") et que sa sortie contient un token GitHub (ghp_...) ou une clé OpenAI (sk-...), le plugin remplace le secret par [SECRET_MASQUÉ] dans event.result.content et event.result.output avant que le message role: "tool" ne parte sur le réseau !

Code Source Complet et Commenté (Architecture OpenCode V2) : .opencode/plugins/security-guard-v2.ts

import { Plugin } from "@opencode/plugin"

// 1. Utilitaire de mutation sur place (Règle d'Or n°1) :
//    Conserve la même référence mémoire pour que le moteur V2 prenne en compte la modification
function replaceInPlace(target: Record, next: Record) {
  for (const key of Object.keys(target)) delete target[key]
  Object.assign(target, next)
}

// 2. Utilitaire DLP : masque les clés secrètes avant qu'elles n'atteignent le LLM
function maskSecrets(text: string): string {
  return text
    .replace(/ghp_[A-Za-z0-9]{20,}/g, "[SECRET_GITHUB_MASQUÉ]")
    .replace(/sk-[A-Za-z0-9\-_]{20,}/g, "[SECRET_OPENAI_MASQUÉ]")
}

// 3. Définition officielle d'un plugin OpenCode V2 ({ id, setup })
export default Plugin.define({
  id: "enterprise.security-guard-v2",

  async setup(ctx) {
    // État isolé PAR activation de workspace (Règle d'Or n°3 : jamais en variable globale !)
    let active = true
    const sessionModels = new Map()

    // =========================================================================
    // A. HOOK DE SESSION : Tracer quel modèle LLM est utilisé par session
    // =========================================================================
    await ctx.session.hook("model.request", (ev: any) => {
      if (!active || !ev?.sessionID) return
      const modelName = typeof ev.model === "string" ? ev.model : ev.model?.modelID
      sessionModels.set(ev.sessionID, modelName ?? "unknown")
    })

    // =========================================================================
    // B. HOOK AVANT OUTIL : Bloquer un appel interdit ou réécrire event.input
    // =========================================================================
    await ctx.tool.hook("execute.before", async (event: any) => {
      if (!active) return

      // Règle 1 : Interdire la fusion automatique de Pull Request via MCP
      if (event.tool === "github-mcp-server_merge_pull_request") {
        throw new Error(
          "Sécurité : Fusion directe de PR interdite. Publie uniquement un commentaire."
        )
      }

      // Règle 2 : Forcer HTTPS sur l'outil webfetch en modifiant event.input sur place
      if (event.tool === "webfetch" && typeof event.input?.url === "string") {
        if (event.input.url.startsWith("http://")) {
          replaceInPlace(event.input, {
            ...event.input,
            url: event.input.url.replace("http://", "https://")
          })
        }
      }
    })

    // =========================================================================
    // C. HOOK APRÈS OUTIL : Purger les secrets de event.result (Règle d'Or n°2)
    // =========================================================================
    await ctx.tool.hook("execute.after", async (event: any) => {
      // On ne traite que les exécutions terminées avec succès sur un workspace actif
      if (!active || event.status !== "completed" || !event.result) return

      // 1. Nettoyer event.result.content (le tableau de blocs lu par le LLM en V2)
      if (Array.isArray(event.result.content)) {
        event.result.content = event.result.content.map((part: any) =>
          part?.type === "text" && typeof part.text === "string"
            ? { ...part, text: maskSecrets(part.text) }
            : part
        )
      }

      // 2. Nettoyer aussi event.result.output (chaîne brute ou objet structuré)
      if (typeof event.result.output === "string") {
        event.result.output = maskSecrets(event.result.output)
      } else if (event.result.output && typeof event.result.output.output === "string") {
        event.result.output = {
          ...event.result.output,
          output: maskSecrets(event.result.output.output)
        }
      }
    })

    // =========================================================================
    // D. FONCTION DE NETTOYAGE (appelée quand le workspace se ferme / recharge)
    // =========================================================================
    return async () => {
      active = false
      sessionModels.clear()
    }
  }
})
Astuce Avancée : Comment rendre un même fichier compatible V1 ET V2 (Dual Plugin) ?
Dans un parc où certains développeurs utilisent encore OpenCode CLI 1.x (V1) et d'autres OpenCode Desktop 2.x (V2), on peut attacher les propriétés V2 (.id et .setup) directement sur la fonction V1, comme le fait openintercept-v2.ts : 
// 1. Fonction pour les moteurs V1 :
const MyDualPlugin = async (ctx: any) => ({
  "tool.execute.before": async (input: any, output: any) => { /* Logique V1 */ }
})

// 2. Propriétés attachées pour les moteurs V2 :
;(MyDualPlugin as any).id = "enterprise.security-guard"
;(MyDualPlugin as any).setup = async (ctx: any) => { /* Logique V2 */ }

export default MyDualPlugin

4. L'Équivalent Exact dans Cursor : .cursor/hooks.json + Script Node.js

Comment obtenir exactement le même contrôle déterministe dans Cursor ? Alors qu'OpenCode V2 exécute setup(ctx) directement en mémoire dans son processus Bun, Cursor utilise un fichier .cursor/hooks.json qui lance un script externe à chaque événement en lui passant le contexte en JSON sur l'entrée standard (stdin) :

⚙️ 1. Fichier de Configuration Cursor : .cursor/hooks.json
{
  "version": 1,
  "hooks": {
    "beforeMCPExecution": [
      { "command": "node .cursor/hooks/security-guard.js" }
    ],
    "beforeShellExecution": [
      { "command": "node .cursor/hooks/security-guard.js" }
    ],
    "beforeReadFile": [
      { "command": "node .cursor/hooks/security-guard.js" }
    ]
  }
}
📜 2. Script Hook Cursor : .cursor/hooks/security-guard.js
// Cursor envoie le JSON de l'action en cours sur STDIN
let raw = ""
process.stdin.on("data", chunk => (raw += chunk))
process.stdin.on("end", () => {
  const event = JSON.parse(raw)

  // Bloquer la fusion de Pull Request via MCP dans Cursor
  if (event.tool_name === "merge_pull_request") {
    console.log(JSON.stringify({
      permission: "deny",
      user_message: "Fusion directe de PR interdite par .cursor/hooks.json",
      agent_message: "Action refusée : publie uniquement un commentaire."
    }))
    process.exit(0)
  }

  // Autoriser l'exécution par défaut
  console.log(JSON.stringify({ permission: "allow" }))
})
