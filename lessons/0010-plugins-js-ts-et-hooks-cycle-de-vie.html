Programmer la Boucle Agentique : Plugins JS/TS (@opencode-ai/plugin) & Hooks

Les Rules (Étape 7) et les Skills (Étape 8) ne sont que du texte Markdown que le LLM peut parfois ignorer. Voyons comment brancher du vrai code JavaScript/TypeScript au cœur de l'agent pour contrôler ses actions à 100%.

📖 Fil Rouge Architectural • Chapitre 10
Jusqu'ici, nous avons guidé le LLM avec du texte Markdown (AGENTS.md, SKILL.md). Mais que se passe-t-il si un outil lit un fichier de logs contenant par erreur un mot de passe ou une clé API sk-live-... ? Avant même que le LLM ne puisse lire une règle lui disant « ignore ce secret », la clé a déjà quitté votre ordinateur dans le message HTTP role: "tool" (Étape 4) ! Pour garantir la sécurité, il nous faut du code déterministe qui s'exécute avant et après les outils.
🔴 Le Problème : Le Markdown est Probabiliste
Écrire « N'exécute jamais rm -rf et ne lis jamais les secrets » dans AGENTS.md est un conseil donné au LLM, pas une barrière technique. Si le modèle hallucine ou subit une attaque par Prompt Injection, il peut violer la consigne.
🟢 La Solution : Les Plugins & Hooks Déterministes
OpenCode permet de déposer des fichiers .js ou .ts dans .opencode/plugins/ (et Cursor utilise .cursor/hooks.json). Ce code s'intercale physiquement dans la boucle de l'agent pour inspecter, modifier ou bloquer les requêtes et les outils avec une garantie mathématique de 100%.

1. Les Fondations : Qu'est-ce qu'un Plugin OpenCode et comment ça marche ?

Oubliez toute complexité : un plugin OpenCode est simplement un fichier JavaScript (.js) ou TypeScript (.ts) posé dans le dossier .opencode/plugins/ de votre projet (ou ~/.config/opencode/plugins/ pour tous vos projets).

Au démarrage d'OpenCode, le moteur lit ce fichier et exécute la fonction qu'il exporte. Voici le squelette minimal de tout plugin : 

// Fichier : .opencode/plugins/mon-premier-plugin.js
// 1. OpenCode appelle votre fonction au démarrage et lui passe un objet de contexte (ctx)
export const MonPremierPlugin = async (ctx) => {

  // 2. Votre fonction retourne un objet contenant les "Hooks" (points d'interception)
  //    auxquels vous souhaitez vous abonner dans la boucle agentique :
  return {
    // Point d'interception A : Modifier le System Prompt (Étape 1)
    // Point d'interception B : Ajouter un nouvel outil dans tools[] (Étape 2)
    // Point d'interception C : Intercepter un outil AVANT son exécution (Étape 4)
    // Point d'interception D : Intercepter un outil APRÈS son exécution (Étape 4)
  }
}

A. Que contient l'objet ctx reçu en paramètre à la ligne 3 ?

Lorsqu'OpenCode lance votre plugin, il vous donne accès à l'environnement local via l'argument ctx (souvent déstructuré en { directory, $ }) :

Propriété de ctx Qu'est-ce que c'est ? Exemple d'utilisation concrète
ctx.directory Une simple chaîne de caractères contenant le chemin du dossier de travail actuel. "/Users/alice/mon-projet"
ctx.$ (BunShell) L'utilitaire fourni par le runtime Bun pour exécuter une commande shell locale en une ligne (sans avoir à importer child_process). const branch = await ctx.$`git branch --show-current`.text()
(Exécute la commande Git et récupère le texte de sortie).
ctx.project / ctx.worktree Informations sur le projet et la racine du dépôt Git courant. Vérifier si l'agent travaille dans une branche Git isolée.

B. Quelles sont les 4 clés que votre plugin peut retourner (et leur lien avec les Étapes 1 à 4) ?

Tout ce que fait un plugin se résume à 4 clés principales dans l'objet `return { ... }`. Chacune agit sur une étape précise du protocole OpenAI que nous avons étudiée dans l'Acte I :

Clé retournée par le Plugin Quand est-elle appelée ? Paramètres reçus (input, output)
1. "tool.execute.before" Juste AVANT qu'OpenCode n'exécute un outil demandé par le LLM. • input.tool : nom de l'outil (ex: "bash", "read")
• output.args : les arguments JSON choisis par le LLM (ex: { command: "npm test" }).
👉 Si vous faites throw new Error("Refusé"), l'outil n'est PAS exécuté !
2. "tool.execute.after" Juste APRÈS l'exécution de l'outil, mais AVANT que le résultat ne soit envoyé au LLM dans role: "tool". • input.tool : nom de l'outil qui vient de tourner
• output.output : le texte brut renvoyé par l'outil (stdout ou contenu du fichier).
👉 Vous pouvez modifier output.output pour masquer un secret avant qu'il ne parte sur le réseau !
3. "experimental.chat.system.transform" Avant chaque requête HTTP envoyée à /v1/chat/completions. • output.system : le tableau des textes qui forment le message role: "system".
👉 Faites output.system.push("...") pour injecter une consigne dynamique.
4. tool: { ... } Au démarrage de l'agent lors de la création du catalogue tools[] (Étape 2). Utilise la fonction tool({ description, args, execute }) du SDK @opencode-ai/plugin pour créer un nouvel outil en TypeScript avec Zod.
Règle importante : Pourquoi modifie-t-on directement l'objet output ?
Dans les hooks d'OpenCode, vous remarquerez que l'on n'utilise pas return pour renvoyer la valeur modifiée : on modifie directement les propriétés de l'objet output passé en second paramètre (ex: output.output = ... ou output.system.push(...)). C'est exactement comme l'objet res dans un middleware Express.js : OpenCode passe le même objet output à tous vos plugins, puis lit son contenu final.

PARTIE 1 • Comprendre les Bases : 3 Mini-Plugins de 10 Lignes (1 Concept à la Fois)

Pour bien comprendre l'effet exact sur la requête HTTP envoyée au LLM, prenons 3 exemples ultra-courts, chacun illustrant une seule fonctionnalité.

Exemple 1A : Bloquer un outil dangereux avec tool.execute.before (10 lignes)

Imaginons que le LLM tente de lire votre fichier .env via l'outil natif read. Voici comment l'intercepter et le bloquer en JavaScript pur :

📄 Code du Plugin (.opencode/plugins/block-env.js)
export const BlockEnvPlugin = async () => {
  return {
    // Appelé juste avant qu'OpenCode n'exécute n'importe quel outil
    "tool.execute.before": async (input, output) => {
      // input.tool = nom de l'outil ("read", "bash", etc.)
      // output.args = arguments envoyés par le LLM
      if (input.tool === "read" && output.args.filePath.includes(".env")) {
        // Lever une erreur annule immédiatement la lecture du fichier !
        throw new Error("Accès refusé : interdiction de lire un fichier .env")
      }
    }
  }
}
📡 Impact sur le Payload HTTP envoyé au LLM (Étape 4)

Le fichier .env n'est jamais ouvert sur le disque. OpenCode capture votre Error et l'envoie au LLM dans le message role: "tool" pour qu'il comprenne pourquoi son action a été refusée : 

{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "Error: Accès refusé : interdiction de lire un fichier .env"
}

Exemple 1B : Ajouter du contexte dans le System Prompt avec system.transform (10 lignes)

Vous voulez que le LLM connaisse toujours le dossier courant sans que le développeur ait à l'écrire :

📄 Code du Plugin (.opencode/plugins/inject-context.js)
export const InjectContextPlugin = async ({ directory }) => {
  return {
    // Appelé juste avant chaque requête POST /v1/chat/completions
    "experimental.chat.system.transform": async (input, output) => {
      // On ajoute notre phrase dans le tableau output.system
      output.system.push(
        `Information Runtime : le projet actif est situé dans ${directory}.`
      )
    }
  }
}
📡 Impact sur le Payload HTTP envoyé au LLM (Étape 1)

Dans la requête HTTP vers /v1/chat/completions, le premier message messages[0] contient désormais automatiquement votre phrase : 

{
  "messages": [
    {
      "role": "system",
      "content": "Tu es OpenCode...\n\nInformation Runtime : le projet actif est situé dans /Users/alice/app."
    }
  ]
}

Exemple 1C : Créer un nouvel outil avec tool(), Zod et BunShell ($) (18 lignes)

Vous voulez donner au LLM un nouvel outil sur mesure nommé git_last_commits qui retourne les N derniers commits Git. C'est ici qu'interviennent tool.schema (Zod) pour décrire le paramètre `count`, et $ (BunShell) pour lancer la commande `git log` :

📄 Code du Plugin (.opencode/plugins/git-tool.ts)
import { type Plugin, tool } from "@opencode-ai/plugin"

export const GitToolPlugin: Plugin = async ({ $ }) => {
  return {
    tool: {
      // Nom de l'outil qui apparaîtra dans tools[]
      git_last_commits: tool({
        description: "Récupère les N derniers commits Git du projet",
        args: {
          // Zod (via tool.schema) définit un entier obligatoire
          count: tool.schema.number().int().describe("Nombre de commits à lire")
        },
        // Fonction exécutée quand le LLM appelle cet outil
        async execute(args) {
          // BunShell ($) exécute git log et retourne le texte
          return await $`git log -n ${args.count} --oneline`.text()
        }
      })
    }
  }
}
📡 Impact sur le Payload HTTP envoyé au LLM (Étape 2)

Grâce à tool.schema (Zod), OpenCode génère automatiquement ce JSON Schema et l'ajoute au tableau tools[] envoyé au LLM : 

{
  "type": "function",
  "function": {
    "name": "git_last_commits",
    "description": "Récupère les N derniers commits Git du projet",
    "parameters": {
      "type": "object",
      "properties": {
        "count": {
          "type": "integer",
          "description": "Nombre de commits à lire"
        }
      },
      "required": ["count"]
    }
  }
}

PARTIE 2 • Cas Réel d'Industrialisation : Sécuriser une Revue de PR (Plugin + MCP + Skill)

Maintenant que les bases sont claires, voyons comment une équipe d'ingénierie combine MCP (Étape 5), un Skill (Étape 8) et un Plugin de sécurité dans un cas réel d'entreprise :

  • L'agent dispose du serveur MCP GitHub pour inspecter et commenter les Pull Requests.
  • Mais la politique de sécurité de l'entreprise impose 3 garde-fous stricts :
    1. Avant l'outil (tool.execute.before) — Bloquer le Merge : L'agent a le droit de commenter une PR, mais il lui est formellement interdit d'appeler l'outil MCP github_merge_pull_request.
    2. Avant l'outil (tool.execute.before) — Forcer HTTPS : Si l'agent appelle l'outil webfetch avec une URL en http://, le plugin la réécrit automatiquement en https:// avant que la requête ne parte.
    3. Après l'outil (tool.execute.after) — Masquer les Secrets (DLP) : Si un fichier lu ou un diff Git contient par erreur un token GitHub (ghp_...) ou une clé OpenAI (sk-...), le plugin remplace le secret par [SECRET_MASQUÉ] avant qu'OpenCode ne l'envoie vers les serveurs d'OpenAI dans role: "tool" !

Code Source Complet et Commenté : .opencode/plugins/security-guard.ts

import { type Plugin } from "@opencode-ai/plugin"

// Fonction utilitaire qui remplace les clés API (sk-..., ghp_...) par [SECRET_MASQUÉ]
function maskSecrets(text: string): string {
  return text
    .replace(/ghp_[A-Za-z0-9]{20,}/g, "[SECRET_GITHUB_MASQUÉ]")
    .replace(/sk-[A-Za-z0-9\-_]{20,}/g, "[SECRET_OPENAI_MASQUÉ]")
}

export const SecurityGuardPlugin: Plugin = async () => {
  return {
    // =========================================================================
    // 1. AVANT L'EXÉCUTION DE L'OUTIL (Validation & Réécriture des arguments)
    // =========================================================================
    "tool.execute.before": async (input, output) => {
      // Règle A : Interdire totalement la fusion d'une Pull Request via MCP
      if (input.tool === "github-mcp-server_merge_pull_request") {
        throw new Error(
          "Sécurité : La fusion automatique de PR est interdite. Publie uniquement un commentaire."
        )
      }

      // Règle B : Si l'outil est "webfetch", remplacer http:// par https:// dans output.args.url
      if (input.tool === "webfetch" && typeof output.args.url === "string") {
        if (output.args.url.startsWith("http://")) {
          output.args.url = output.args.url.replace("http://", "https://")
        }
      }
    },

    // =========================================================================
    // 2. APRÈS L'EXÉCUTION DE L'OUTIL (Purge des secrets avant envoi au LLM)
    // =========================================================================
    "tool.execute.after": async (input, output) => {
      // output.output contient le texte brut retourné par l'outil (read, bash, MCP...)
      // On masque tout secret AVANT que ce texte ne soit mis dans le message role: "tool" !
      if (typeof output.output === "string") {
        output.output = maskSecrets(output.output)
      }
    }
  }
}

export default SecurityGuardPlugin

3. L'Équivalent Exact dans Cursor : .cursor/hooks.json + Script Node.js

Comment obtenir exactement le même blocage déterministe dans Cursor ? Alors qu'OpenCode charge un plugin JS/TS directement dans son processus mémoire, Cursor utilise un fichier .cursor/hooks.json qui lance un script externe en lui passant les informations de l'outil en JSON sur l'entrée standard (stdin) :

⚙️ 1. Fichier de Configuration Cursor : .cursor/hooks.json
{
  "version": 1,
  "hooks": {
    "beforeMCPExecution": [
      { "command": "node .cursor/hooks/security-guard.js" }
    ],
    "beforeShellExecution": [
      { "command": "node .cursor/hooks/security-guard.js" }
    ],
    "beforeReadFile": [
      { "command": "node .cursor/hooks/security-guard.js" }
    ]
  }
}
📜 2. Script Hook Cursor : .cursor/hooks/security-guard.js
// Cursor envoie le JSON de l'action en cours sur STDIN
let raw = ""
process.stdin.on("data", chunk => (raw += chunk))
process.stdin.on("end", () => {
  const event = JSON.parse(raw)

  // Bloquer la fusion de Pull Request via MCP dans Cursor
  if (event.tool_name === "merge_pull_request") {
    console.log(JSON.stringify({
      permission: "deny",
      user_message: "Fusion directe de PR interdite par .cursor/hooks.json",
      agent_message: "Action refusée : publie uniquement un commentaire."
    }))
    process.exit(0)
  }

  // Autoriser l'exécution par défaut
  console.log(JSON.stringify({ permission: "allow" }))
})
Dimension Technique OpenCode (.opencode/plugins/*.ts) Cursor (.cursor/hooks.json)
Modèle d'Exécution In-Process (Bun) : Fonction JS/TS chargée une seule fois en mémoire vive au démarrage. Sous-processus Externe : Lance le script configuré à chaque événement et communique via JSON sur stdin / stdout.
Création de Nouveaux Outils Oui : Via la clé tool: { ... } et tool.schema (Zod) directement dans le plugin. Non : Les hooks Cursor servent uniquement à autoriser/bloquer ; pour ajouter un outil dans Cursor, il faut utiliser un serveur MCP (Étape 5).
Interception Avant Outil Hook "tool.execute.before" (modification de output.args ou throw new Error). Hooks beforeShellExecution / beforeMCPExecution / beforeReadFile retournant {"permission": "deny"}.
Interception Après Outil Hook "tool.execute.after" (permet de réécrire output.output avant l'envoi au LLM). Hooks afterFileEdit / stop (observation post-action).
