La Boucle Agentique (ReAct) : Rôle tool, Boucle while & Permissions

Découvrez comment OpenCode et Cursor transforment une simple API HTTP sans mémoire en un véritable agent autonome grâce au cycle ReAct (Reason + Act + Observe) et au message "role": "tool".

📖 Fil Rouge Architectural • Chapitre 4
À l'Étape 3, notre premier appel HTTP s'est arrêté sur finish_reason: "tool_calls" : le LLM nous a demandé de lire le fichier src/auth.ts (avec l'identifiant call_abc123xyz). Mais comme l'API OpenAI est stateless (Étape 1), la connexion HTTP est terminée et le serveur d'OpenAI n'attend rien ! C'est maintenant à notre programme local (OpenCode ou Cursor) de lire réellement src/auth.ts sur le disque dur, puis de renvoyer son contenu au LLM dans une seconde requête HTTP.

1. Qu'est-ce que « ReAct » ? (La Définition Fondamentale)

En intelligence artificielle, ReAct est la contraction de Reason (Raisonner) + Act (Agir). Ce concept, introduit en 2022 par des chercheurs de Princeton et Google ("ReAct: Synergizing Reasoning and Acting in Language Models"), est le patron d'architecture qui propulse tous les agents de code modernes (OpenCode, Cursor, Claude Code).

Au lieu de répondre tout de suite au hasard (et d'halluciner sur un code qu'il n'a pas vu), un agent ReAct fonctionne dans une boucle en 3 temps qui se répète jusqu'à ce qu'il ait toutes les informations pour répondre :

Étape du Cycle ReAct Qui travaille ? Traduction concrète dans le protocole HTTP OpenAI
1. 🧠 Reason (Raisonner) Le Serveur LLM (Cloud) Le LLM lit l'historique messages[] et se dit : « Pour répondre à l'utilisateur sur l'authentification, j'ai d'abord besoin de lire le fichier src/auth.ts. »
2. ⚡ Act (Agir) Le Serveur LLM → L'Agent Local Le LLM stoppe sa génération avec "finish_reason": "tool_calls" et envoie l'ordre JSON : name: "read", arguments: "{\"filePath\":\"src/auth.ts\"}" (Étape 3).
3. 👁️ Observe (Observer) L'Agent Local → Le Serveur LLM Votre agent local (OpenCode / Cursor) lit src/auth.ts sur votre disque dur et renvoie son contenu au LLM dans un nouveau message "role": "tool" pour que le LLM puisse observer le résultat et continuer à raisonner !

2. Comment envoyer l'Observation au LLM : Le Message "role": "tool"

Reprenons exactement là où nous nous sommes arrêtés à l'Étape 3. Le développeur a demandé : « Lis les 50 premières lignes du fichier src/auth.ts et dis-moi quelle variable d'environnement est utilisée ».

Après avoir lu le fichier localement, OpenCode effectue un second appel HTTP POST /v1/chat/completions. Pour que le LLM comprenne à quelle demande correspond ce résultat, OpenAI impose une règle stricte :

Règle d'Or du Protocole OpenAI (Corrélation tool_call_id) :
Dans le tableau messages[] du second appel HTTP, vous devez conserver les messages précédents (system et user), ajouter le message "role": "assistant" qui contenait le tool_calls (avec son id: "call_abc123xyz"), et placer juste après le message "role": "tool" contenant exactement le même "tool_call_id": "call_abc123xyz". Si vous oubliez l'un des deux, l'API renvoie une erreur HTTP 400 Bad Request. 
# SECOND APPEL HTTP (Tour 2 de la boucle ReAct) :
# Le tableau messages[] contient maintenant 4 messages !
curl https://api.openai.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [
      {
        "role": "system",
        "content": "Tu es un agent de développement. Utilise les outils mis à ta disposition."
      },
      {

      },
      {
        "role": "assistant",
        "content": null,
        "tool_calls": [
          {
            "id": "call_abc123xyz",
            "type": "function",
            "function": {
              "name": "read",
              "arguments": "{\"filePath\":\"src/auth.ts\",\"offset\":0,\"limit\":50}"
            }
          }
        ]
      },
      {
        "role": "tool",
        "tool_call_id": "call_abc123xyz",

      }

Pourquoi appelle-t-on cela une « Boucle » (while) ?

Dans notre exemple ci-dessus, un seul outil (read) a suffi : la boucle a donc fait 1 tour d'outil (soit 2 appels HTTP au total).
Mais si après avoir lu src/auth.ts à l'étape 6, le LLM avait voulu vérifier si JWT_SECRET était bien défini dans .env.example, il aurait à nouveau répondu finish_reason: "tool_calls" ! Le code interne d'OpenCode et de Cursor tient donc en une simple boucle while : 

// Le cœur exact d'un agent IA (OpenCode / Cursor) en 15 lignes :
while (true) {
  // 1. On envoie tout l'historique messages[] au serveur LLM
  const response = await callOpenAI(messages, tools)
  const choice = response.choices[0]

  // 2. On ajoute toujours la réponse du LLM à l'historique
  messages.push(choice.message)

  // 3. Si le LLM a fini (finish_reason === "stop"), on sort de la boucle !
  if (choice.finish_reason !== "tool_calls") {
    return choice.message.content
  }

  // 4. Sinon (finish_reason === "tool_calls"), on exécute chaque outil demandé
  //    et on ajoute le résultat "role": "tool" avant de refaire un tour de boucle !
  for (const toolCall of choice.message.tool_calls) {
    const output = await executeLocalTool(toolCall.function.name, toolCall.function.arguments)
    messages.push({
      role: "tool",
      tool_call_id: toolCall.id,
      content: output
    })
  }
}

4. Gouvernance & Permissions (Étape 4 du Diagramme) : OpenCode vs Cursor

À l'étape 4 du diagramme ci-dessus, juste avant d'exécuter un outil sur votre machine, comment éviter qu'une hallucination du LLM n'exécute rm -rf / ou ne lise vos secrets dans .env ? OpenCode et Cursor intègrent un pare-feu déclaratif de permissions :

⚙️ Configuration Officielle OpenCode (opencode.jsonc)
// Clé officielle "permission" ("allow" | "ask" | "deny")
// Règle d'évaluation : le DERNIER motif glob correspondant l'emporte ("*" en premier)
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "*": "ask",
    "edit": "ask",
    "bash": {
      "*": "ask",
      "git status *": "allow",
      "git diff *": "allow",
      "git push *": "deny"
    },
    "read": {
      "*": "allow",
      "*.env*": "ask"
    }
  }
}
⚙️ Configuration Équivalente Cursor (.cursor/cli.json & .cursorignore)
// 1. Fichier .cursor/cli.json (Permissions CLI & Agent : deny l'emporte sur allow)
{
  "permissions": {
    "allow": [
      "Shell(git status)",
      "Shell(git diff)",
      "Read(src/**)"
    ],
    "deny": [
      "Shell(git push)",
      "Shell(rm -rf *)",
      "Read(.env*)"
    ]
  }
}

// 2. Fichier .cursorignore (Bloque l'indexation et la lecture par l'agent)
// .env*
// secrets/**
Mécanisme de Sécurité OpenCode (Documentation Officielle) Cursor (Documentation Officielle)
Niveaux de décision "allow" (exécution directe), "ask" (demande confirmation au développeur), "deny" (bloqué, même avec --auto). Mode standard (demande confirmation sur terminal/édition) vs Auto-Run avec .cursor/permissions.json et .cursor/cli.json.
Filtrage granulaire de commandes Shell Objet "permission": { "bash": { "*": "ask", "git status *": "allow" } } dans opencode.jsonc (le dernier motif correspondant gagne). terminalAllowlist dans .cursor/permissions.json ou directives Shell(...) dans .cursor/cli.json (où deny est prioritaire).
Protection des fichiers sensibles Règle "read": { "*": "allow", "*.env*": "ask" } ou "deny" dans permission. Fichier .cursorignore + règle Read(.env*) dans la liste deny de .cursor/cli.json.

5. Gestion des Erreurs & Troncature des Sorties (Output Pruning)

Que fait l'agent si la commande exécutée échoue (code de sortie exit 1) ou renvoie 50 Mo de logs ?

  • Auto-correction (Self-Healing grâce à ReAct) : L'agent ne plante pas sur une erreur d'outil. Il capture le message d'erreur (stderr) et l'envoie au LLM dans le message "role": "tool". En observant l'erreur, le LLM corrige sa commande au tour suivant !
  • Troncature (Context Pruning) : Pour éviter une erreur context_length_exceeded, OpenCode tronque automatiquement les sorties d'outils dépassant un seuil (~2 000 lignes ou 30 KB) avant de les insérer dans role: "tool".
