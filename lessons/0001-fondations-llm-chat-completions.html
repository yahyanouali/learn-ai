Le Cerveau Isolé : API REST /v1/chat/completions, Statelessness & Rôles

Toute architecture d'agent (OpenCode, Cursor, Claude Code) repose sur une brique fondamentale : une requête HTTP POST vers un serveur d'inférence. Ouvrons le capot réseau avant d'ajouter la moindre couche d'abstraction.

📖 Fil Rouge Architectural • Chapitre 1
Nous partons de zéro : pas d'IDE magique, pas de SDK opaque. Nous voulons comprendre comment un client local (un terminal, OpenCode ou Cursor) dialogue sur le réseau avec un grand modèle de langage (LLM), pourquoi ce dernier est structurellement amnésique d'une requête à l'autre, et comment l'agent maintient la mémoire de la conversation côté client.
🔴 Le Problème Technique
Un moteur d'inférence LLM est 100% sans état (Stateless). Contrairement à une base de données ou une session Web stateful, le serveur ne conserve aucune mémoire de votre appel HTTP précédent. Si vous lui envoyez un second message seul, il ignore qui vous êtes et de quel fichier vous parliez 2 secondes plus tôt.
🟢 La Solution Architecturale
C'est le client local (OpenCode ou Cursor) qui joue le rôle de mémoire : il maintient sur votre machine un tableau ordonné de messages (messages[]) segmenté par rôles (system, user, assistant, tool) et retransmet l'historique complet à chaque appel POST /v1/chat/completions.

1. Le Contrat Réseau Universel : POST /v1/chat/completions

Qu'un agent tourne dans un terminal TUI comme OpenCode ou dans un éditeur forké de VS Code comme Cursor, sa boucle centrale finit toujours par sérialiser une requête HTTP conforme à la spécification OpenAI Chat Completions. Ce contrat est devenu le standard de facto de l'industrie (supporté par OpenAI, Anthropic via adaptateurs, OpenRouter, OmniRoute, vLLM, Ollama et LiteLLM). 

curl https://api.openai.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "model": "gpt-4o-mini",
    "temperature": 0.1,
    "messages": [
      {
        "role": "system",
        "content": "Tu es un ingénieur logiciel senior spécialisé en architecture distribuée. Réponds de manière concise et rigoureuse."
      },
      {
        "role": "user",
        "content": "Explique pourquoi une API d'\''inférence LLM est stateless."
      }
    ]
  }'

2. Anatomie de la Pile de Messages (messages[]) et Déterminisme

Dans l'architecture des transformeurs (Decoder-only Transformers), toute la conversation est concaténée en une seule séquence de tokens à l'intérieur de la fenêtre de contexte (Context Window), délimitée par des marqueurs spéciaux de contrôle propres à chaque rôle :

Rôle Protocolaire Émetteur Responsabilité dans l'Ingénierie du Contexte
"role": "system" Le Runtime Agent (OpenCode / Cursor) Autorité maximale (System Prompt) : Définit l'identité de l'agent, les contraintes d'architecture, les règles du projet (AGENTS.md) et l'environnement système. Toujours placé à l'index 0.
"role": "user" Le Développeur Requête entrante : Contient la consigne de l'utilisateur ainsi que les fragments de fichiers explicitement attachés (via @fichier dans Cursor ou OpenCode).
"role": "assistant" Le Modèle (LLM) Sortie générée : Contient soit la réponse textuelle du modèle, soit une demande d'exécution d'outil (tool_calls, que nous étudierons aux Étapes 2 et 3).
"role": "tool" Le Runtime Agent Retour d'exécution locale : Transporte la sortie standard (stdout / stderr) d'un outil exécuté sur la machine hôte vers le modèle (Étape 4).

3. Comment l'Agent Simule une Mémoire face à une API Stateless

Puisque le serveur LLM oublie tout sitôt sa réponse HTTP envoyée, c'est l'agent local (OpenCode ou Cursor) qui stocke la conversation sur votre disque et **empile les échanges dans le tableau `messages[]`** à chaque nouveau tour :

sequenceDiagram actor Dev as Développeur participant Agent as Runtime Client (OpenCode / Cursor) participant LLM as Serveur API LLM (Stateless) Note over Dev,LLM: TOUR 1 : Premier échange Dev->>Agent: 1. "Analyse le bug dans auth.ts" Agent->>LLM: 2. POST /v1/chat/completions [system, user1] LLM-->>Agent: 3. Réponse assistant1 ("Le bug vient de verifyToken...") Note over Agent: Sauvegarde [system, user1, assistant1] en mémoire locale Agent-->>Dev: 4. Affiche la réponse assistant1 Note over Dev,LLM: TOUR 2 : Le client renvoie tout l'historique accumulé Dev->>Agent: 5. "Corrige cette fonction" Note over Agent: Ajoute user2 à la suite du tableau messages[] Agent->>LLM: 6. POST /v1/chat/completions [system, user1, assistant1, user2] LLM-->>Agent: 7. Réponse assistant2 (Correctif proposé) Agent-->>Dev: 8. Affiche la réponse assistant2
Conséquence directe — La Fenêtre de Contexte (Context Window) :
Puisque le tableau messages[] grandit à chaque tour (questions, réponses, fichiers lus, sorties de commandes), sa taille totale en tokens augmente en continu. Toute l'ingénierie des agents modernes (que nous verrons dans les Actes II et III avec le Code Mode, les Skills et les Sous-Agents) consiste à éviter que ce tableau ne devienne trop volumineux !

4. Comparaison Architecturale : OpenCode vs Cursor

Critère Technique OpenCode (TUI / Desktop / CLI) Cursor (IDE Fork VS Code)
Gestion de l'état de session Stocké localement sur disque (SQLite / JSONL de session). Le client reconstruit messages[] à chaque tour. Stocké dans la base locale de l'espace de travail Cursor (SQLite state.vscdb) et relayé via le backend Cursor.
Transport Réseau Appel direct du client local vers le provider configuré dans opencode.jsonc (OpenAI, Anthropic, OmniRoute, LMStudio). Appel du client IDE vers le proxy cloud Cursor (qui route ensuite vers le modèle cible), ou clé API directe.
Inspection du Payload HTTP Transparente et interceptable via un plugin local (dans ~/.config/opencode/plugins/). Fermée côté proxy Cursor (visible uniquement via les compteurs de tokens dans l'interface).
