Le Cerveau Isolé : API REST /v1/chat/completions, Statelessness & Rôles

Toute architecture d'agent (OpenCode, Cursor, Claude Code) repose sur une brique fondamentale : une requête HTTP POST vers un serveur d'inférence. Ouvrons le capot réseau avant d'ajouter la moindre couche d'abstraction.

📖 Fil Rouge Architectural • Chapitre 1
Nous partons de zéro : pas d'IDE magique, pas de SDK opaque. Nous voulons comprendre comment un client local (un terminal, OpenCode ou Cursor) dialogue sur le réseau avec un grand modèle de langage (LLM), pourquoi ce dernier est structurellement amnésique d'une requête à l'autre, et comment l'agent maintient la mémoire de la conversation côté client.
🔴 Le Problème Technique
Un moteur d'inférence LLM est 100% sans état (Stateless). Contrairement à une base de données ou une session Web stateful, le serveur ne conserve aucune mémoire de votre appel HTTP précédent. Si vous lui envoyez un second message seul, il ignore qui vous êtes et de quel fichier vous parliez 2 secondes plus tôt.
🟢 La Solution Architecturale
C'est le client local (OpenCode ou Cursor) qui joue le rôle de mémoire : il maintient sur votre machine un tableau ordonné de messages (messages[]) segmenté par rôles (system, user, assistant, tool) et retransmet l'historique complet à chaque appel POST /v1/chat/completions.

1. Le Contrat Réseau Universel : POST /v1/chat/completions

Qu'un agent tourne dans un terminal TUI comme OpenCode ou dans un éditeur forké de VS Code comme Cursor, sa boucle centrale finit toujours par sérialiser une requête HTTP conforme à la spécification OpenAI Chat Completions. Ce contrat est devenu le standard de facto de l'industrie (supporté par OpenAI, Anthropic via adaptateurs, OpenRouter, OmniRoute, vLLM, Ollama et LiteLLM). 

curl https://api.openai.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "model": "gpt-4o-mini",
    "temperature": 0.1,
    "messages": [
      {
        "role": "system",
        "content": "Tu es un ingénieur logiciel senior spécialisé en architecture distribuée. Réponds de manière concise et rigoureuse."
      },
      {
        "role": "user",
        "content": "Explique pourquoi une API d'\''inférence LLM est stateless."
      }
    ]
  }'

Le serveur d'inférence traite ce tableau, génère la suite de tokens la plus probable, et renvoie une réponse JSON contenant le message généré ("role": "assistant"), la raison d'arrêt ("finish_reason": "stop") ainsi que le décompte exact de tokens consommés (usage) : 

{
  "id": "chatcmpl-A1B2C3D4E5",
  "object": "chat.completion",
  "created": 1731600000,
  "model": "gpt-4o-mini-2024-07-18",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "Une API d'inférence LLM est stateless car les poids du modèle sont figés en mémoire GPU : chaque requête HTTP doit fournir l'intégralité du contexte nécessaire au calcul d'attention."
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 46,
    "completion_tokens": 38,
    "total_tokens": 84
  }
}

2. Anatomie de la Pile de Messages (messages[]) et Déterminisme

Dans l'architecture des transformeurs (Decoder-only Transformers), toute la conversation est concaténée en une seule séquence de tokens à l'intérieur de la fenêtre de contexte (Context Window), délimitée par des marqueurs spéciaux de contrôle propres à chaque rôle :

Rôle Protocolaire Émetteur Responsabilité dans l'Ingénierie du Contexte
"role": "system"
(ou "developer" sur OpenAI o-series / GPT-4.1+)		 Le Runtime Agent (OpenCode / Cursor) Autorité maximale (System Prompt) : Définit l'identité de l'agent, les contraintes d'architecture, les règles du projet (AGENTS.md) et l'environnement système. Toujours placé à l'index 0 ("system" reste le standard universel multi-fournisseurs).
"role": "user" Le Développeur Requête entrante : Contient la consigne de l'utilisateur ainsi que les fragments de fichiers explicitement attachés (via @fichier dans Cursor ou OpenCode).
"role": "assistant" Le Modèle (LLM) Sortie générée : Contient soit la réponse textuelle du modèle, soit une demande d'exécution d'outil (tool_calls, que nous étudierons aux Étapes 2 et 3).
"role": "tool" Le Runtime Agent Retour d'exécution locale : Transporte la sortie standard (stdout / stderr) d'un outil exécuté sur la machine hôte vers le modèle (Étape 4).

3. Sous le Capot du Serveur et du GPU : Comment un LLM Comprend-il le JSON et les Rôles ?

Une question fondamentale se pose souvent aux développeurs : « Un réseau de neurones ne manipule que des vecteurs de nombres. Comment peut-il comprendre la structure d'un body JSON OpenAI, faire la différence entre role: "system", role: "user" et role: "assistant", ou fabriquer une réponse JSON valide ? »

La réponse tient en une vérité d'architecture essentielle : le LLM ne voit jamais votre JSON applicatif HTTP. C'est le serveur d'inférence (vLLM, SGLang, TGI, Ollama ou le moteur interne d'OpenAI) qui traduit votre JSON en une chaîne de texte plate balisée par des tokens spéciaux. Pour comprendre cette mécanique, distinguons la phase d'entraînement de la phase d'inférence en temps réel.

Partie 1 : Comment le LLM apprend à « jouer son rôle » (L'Entraînement)

Un modèle de langage ne naît pas avec la notion d'utilisateur, d'assistant ou d'outil. Il acquiert cette structure comportementale via trois phases d'apprentissage successives :

📚 1. Le Pré-entraînement (La bibliothèque)

Le modèle lit une fraction significative d'Internet (livres, dépôts GitHub, articles). Son seul but mathématique est de prédire le token suivant. À ce stade (Base Model), c'est un perroquet stochastique surdoué. Si on lui envoie « Bonjour », il peut très bien continuer par « Bonjour, comment ça va ? Bonjour, je m'appelle... » car il imite des suites de dialogues trouvées sur des forums sans savoir qu'on lui pose une question.

🎭 2. Le Post-entraînement / SFT (Le scénario de théâtre)

Lors du Supervised Fine-Tuning (SFT), on lui apprend le format d'un chat. On lui injecte un Chat Template (comme ChatML) qui agit comme un script de théâtre, utilisant des balises invisibles pour l'utilisateur — les tokens spéciaux (chacun relié à un identifiant unique dans le vocabulaire du tokenizer) — tels que <|im_start|> et <|im_end|>.

🛠️ 3. L'Apprentissage des Outils (Tool Calling)

On lui montre des situations de blocage (ex: « Météo à Lyon ? » ou « Lis src/auth.ts »). On lui apprend que la bonne réponse n'est pas d'inventer une température, mais d'écrire une balise spécifique <tool_call> contenant du JSON. Pour le modèle, appeler une API n'est rien d'autre que de produire une syntaxe linguistique apprise !

🧮 Le secret mathématique du SFT : le Loss Masking (Masquage de la Perte)
Pendant que le modèle étudie des millions d'exemples de conversations lors du SFT, on « masque » mathématiquement les consignes system et les questions de l'user (leur poids dans le calcul d'erreur Cross-Entropy Loss est forcé à 0). Le modèle n'est pénalisé — et ne met à jour ses poids synaptiques — que lorsqu'il se trompe sur les mots générés après la balise <|im_start|>assistant.
Il développe ainsi un véritable réflexe de Pavlov mathématique : dès qu'il voit la séquence <|im_start|>assistant\n à la fin du flux d'entrée, il sait que c'est à son tour de parler, et il s'arrête dès qu'il émet le token spécial <|im_end|> !

Partie 2 : La mécanique du serveur en temps réel (L'Aplatissement & l'Inférence GPU)

Lorsque votre client envoie sa requête HTTP POST /v1/chat/completions, le serveur d'inférence (ex: vLLM) applique d'abord un moteur de template (souvent Jinja2) pour aplatir le tableau JSON messages[] en une seule chaîne de texte brute avant de l'envoyer au GPU :

📦 1. Ce que votre code envoie (JSON Applicatif HTTP)
{
  "model": "gpt-4o-mini",
  "messages": [
    {
      "role": "system",
      "content": "Tu es un assistant concis."
    },
    {
      "role": "user",
      "content": "Explique le stateless en 1 phrase."
    }
  ]
}
🧬 2. Ce que le LLM voit réellement sur le GPU (Flux Plat ChatML)
<|im_start|>system
Tu es un assistant concis.<|im_end|>
<|im_start|>user
Explique le stateless en 1 phrase.<|im_end|>
<|im_start|>assistant

Remarquez la dernière ligne du bloc de droite : le serveur d'inférence ajoute délibérément <|im_start|>assistant\n tout à la fin du texte aplati (c'est le paramètre interne add_generation_prompt=True du template Jinja2) pour déclencher le réflexe de génération du modèle ! En production, le GPU exécute alors deux phases matérielles distinctes :

Phase Matérielle GPU Analogie Humaine Mécanique Interne sur la Carte Graphique (VRAM & Tensor Cores)
Phase 1 : Le Prefill
(Parallèle / Compute-Bound)		 La lecture rapide Le serveur prend tout l'historique aplati de la conversation, le transforme en entiers (Token IDs), et le GPU calcule les relations d'attention entre tous ces mots en une seule fois (en parallèle). Le résultat matriciel est stocké dans la mémoire vidéo : c'est le KV Cache (Key-Value Cache, sa mémoire de travail à court terme).
Phase 2 : Le Decode
(Séquentiel / Memory-Bound)		 L'écriture mot à mot Le modèle génère sa réponse token par token. À chaque boucle, il s'appuie sur le KV Cache pour deviner le token suivant le plus probable (sans recalculer le début du texte), l'ajoute au cache, et recommence jusqu'à ce qu'il génère le token de fin <|im_end|> (que le serveur traduit en "finish_reason": "stop").

🔗 Et pour les appels d'outils (tool_calls et role: "tool") ?
C'est exactement la même tuyauterie de traduction entre JSON HTTP et balises de texte plat (<tool_call> et <tool_response>), combinée à la réutilisation du KV Cache ! Nous détaillerons le scénario complet en 7 étapes dès l'Étape 3 : Réception des Tool Calls.

4. Comment l'Agent Simule une Mémoire face à une API Stateless

Puisque le serveur LLM oublie tout sitôt sa réponse HTTP envoyée, c'est l'agent local (OpenCode ou Cursor) qui stocke la conversation sur votre disque et empile les échanges dans le tableau messages[] à chaque nouveau tour :

sequenceDiagram actor Dev as Développeur participant Agent as Runtime Client (OpenCode / Cursor) participant LLM as Serveur API LLM (Stateless) Note over Dev,LLM: TOUR 1 : Premier échange Dev->>Agent: 1. "Analyse le bug dans auth.ts" Agent->>LLM: 2. POST /v1/chat/completions [system, user1] LLM-->>Agent: 3. Réponse assistant1 ("Le bug vient de verifyToken...") Note over Agent: Sauvegarde [system, user1, assistant1] en mémoire locale Agent-->>Dev: 4. Affiche la réponse assistant1 Note over Dev,LLM: TOUR 2 : Le client renvoie tout l'historique accumulé Dev->>Agent: 5. "Corrige cette fonction" Note over Agent: Ajoute user2 à la suite du tableau messages[] Agent->>LLM: 6. POST /v1/chat/completions [system, user1, assistant1, user2] LLM-->>Agent: 7. Réponse assistant2 (Correctif proposé) Agent-->>Dev: 8. Affiche la réponse assistant2
Conséquence directe — La Fenêtre de Contexte (Context Window) :
Puisque le tableau messages[] grandit à chaque tour (questions, réponses, fichiers lus, sorties de commandes), sa taille totale en tokens augmente en continu. Toute l'ingénierie des agents modernes (que nous verrons dans les Actes II et III avec le Code Mode, les Skills et les Sous-Agents) consiste à éviter que ce tableau ne devienne trop volumineux !

5. Comparaison Architecturale : OpenCode vs Cursor

Critère Technique OpenCode (TUI / Desktop / CLI) Cursor (IDE Fork VS Code)
Gestion de l'état de session Stocké localement sur disque (SQLite / JSONL de session). Le client reconstruit messages[] à chaque tour. Stocké dans la base locale de l'espace de travail Cursor (SQLite state.vscdb) et relayé via le backend Cursor.
Transport Réseau Appel direct du client local vers le provider configuré dans opencode.jsonc (OpenAI, Anthropic, OmniRoute, LMStudio). Appel du client IDE vers le proxy cloud Cursor (qui route ensuite vers le modèle cible), ou clé API directe.
Inspection du Payload HTTP Transparente et interceptable via un plugin local (dans ~/.config/opencode/plugins/). Fermée côté proxy Cursor (visible uniquement via les compteurs de tokens dans l'interface).
