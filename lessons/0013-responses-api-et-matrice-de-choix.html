L'Évolution du Standard : OpenAI Responses API (/v1/responses) & Matrice Architecturale Finale

Pour clore notre parcours, comparons le standard universel /v1/chat/completions avec la nouvelle API d'OpenAI /v1/responses, et dressons la synthèse globale de l'architecture d'un agent de code moderne.

📖 Fil Rouge Architectural • Épilogue (Chapitre 13)
Depuis l'Étape 1, nous avons construit un système agentique complet côté client (Client-Managed Agent Loop) sur /v1/chat/completions. Mais OpenAI a également introduit l'endpoint /v1/responses pour unifier Chat Completions et l'ancienne Assistants API. Quel problème cherche-t-il à résoudre, et pourquoi des outils multi-modèles comme OpenCode et Cursor gardent-ils le contrôle local de leur boucle agentique ?
🔴 Le Problème Technique : État Client vs Outils Cloud Hébergés
Lorsque vous construisez un assistant léger pur OpenAI (sans besoin d'accéder aux fichiers locaux d'un poste développeur), gérer manuellement la persistance de messages[] et héberger son propre moteur de recherche Web ou d'indexation vectorielle de PDF demande une infrastructure backend dédiée.
🟢 La Solution Architecturale : Dualité /v1/chat/completions vs /v1/responses
• /v1/responses (Server-Managed / Cloud-Native) : Permet de chaîner l'état côté serveur via previous_response_id et d'exécuter des outils hébergés par OpenAI (web_search_preview, file_search, code_interpreter) en un seul appel.
• /v1/chat/completions (Client-Managed / Multi-Provider) : Reste l'architecture de référence pour les agents locaux (OpenCode, Cursor) qui doivent orchestrer différents fournisseurs (Anthropic, OpenAI, Gemini, DeepSeek, modèles locaux) et exécuter des outils sur le système de fichiers local.

1. Exemple d'Appel à l'API POST /v1/responses

Dans /v1/responses, le tableau messages[] est remplacé par instructions (équivalent du rôle system) et input (chaîne ou tableau d'items), avec chaînage d'état optionnel via previous_response_id : 

curl https://api.openai.com/v1/responses \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "model": "gpt-4o",
    "instructions": "Tu es un architecte logiciel senior.",
    "input": "Recherche les dernières nouveautés de la spécification MCP 2025 et résume-les.",
    "tools": [
      { "type": "web_search_preview" }
    ]
  }'

3. Tableau Comparatif Synthétique : /v1/chat/completions vs /v1/responses

Dimension Architecturale Chat Completions (/v1/chat/completions) Responses API (/v1/responses)
Paramètres d'Entrée Tableau strict messages: [{role, content}] instructions (système) + input (texte ou liste d'items)
Gestion de l'État (Statefulness) 100% Stateless : le client contrôle, élague et renvoie messages[] à chaque tour. Hybride : stateless ou chaîné côté serveur OpenAI via previous_response_id (store: true).
Exécution des Outils Déterministe côté client (le serveur renvoie tool_calls, le client exécute et renvoie role: "tool"). Supporte à la fois les outils natifs exécutés sur les serveurs d'OpenAI et les function_call clients.
Interopérabilité Multi-Modèles Universelle : Standard supporté par tous les fournisseurs et routeurs (OmniRoute, OpenRouter, LiteLLM, vLLM, Ollama). Spécifique à l'écosystème OpenAI (et adaptateurs dédiés aux modèles GPT-5 / o-series).

4. Synthèse Générale des 13 Étapes : L'Architecture Complète d'un Agent Moderne

Vous maîtrisez désormais l'intégralité de la pile technologique d'un agent de développement moderne (OpenCode et Cursor), depuis l'octet transitant sur le socket TCP jusqu'à l'orchestration multi-agents :

  • Acte I (Fondations & Boucle) : Requête HTTP stateless & Rôles (Étape 1) → Contrats JSON Schema tools[] (Étape 2) → Détection de finish_reason: "tool_calls" & SSE (Étape 3) → Boucle ReAct, Permissions allow/ask/deny et role: "tool" (Étape 4).
  • Acte II (Passage à l'Échelle des Outils) : Standardisation externe via JSON-RPC 2.0 MCP (Étape 5) → Orchestration de 100+ outils en sandbox locale via le Code Mode (execute) (Étape 6).
  • Acte III (Ingénierie du Contexte & Gouvernance) : Mémoire permanente avec les Rules AGENTS.md / .mdc (Étape 7) → Savoir-faire chargés à la demande par Progressive Disclosure avec les Skills SKILL.md (Étape 8) → Isolation de la fenêtre de contexte via les Sous-Agents mode: subagent (Étape 9) → Interception déterministe en mémoire vive avec les Plugins JS/TS @opencode-ai/plugin et Hooks (Étape 10).
  • Acte IV (Mise en Production) : Décodage contraint par grammaire strict: true (Étape 11) → Automatisation headless en Pipeline GitLab CI/CD (Étape 12) → Arbitrage architectural entre boucle cliente et /v1/responses (Étape 13).
