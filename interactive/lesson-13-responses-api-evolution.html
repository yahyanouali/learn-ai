L'Évolution du Standard : OpenAI Responses API (/v1/responses)

Long image

A

Answer

La nouvelle API Responses remplace le modèle stateless par une gestion d'état native côté serveur : les tours s'enchaînent simplement via l'identifiant previous_response_id.

  1. Avec /v1/chat/completions, le client est contraint de renvoyer l'intégralité de l'historique à chaque requête HTTP.
  2. Avec /v1/responses, le serveur stocke l'historique et les deltas, allégeant massivement les payloads réseau.
  3. L'API unifie les sorties textuelles, les fichiers générés et l'exécution d'outils hébergés au sein d'un contrat unique.
  4. Cette évolution préfigure le transfert progressif de la boucle agentique du client local vers l'infrastructure d'inférence.

Comment s'enchaînent les requêtes avec la Responses API ?

Le client ne transmet que la nouvelle consigne en référençant la réponse précédente.

Diagram structure
  • Application Cliente client
  • Endpoint POST /v1/responses api
  • Stockage d Etat Serveur store
  • client → api · POST /v1/responses (input: "Cree un projet")
  • api → store · enregistrement session resp_001
  • api → client · 200 OK (id: resp_001, text: "Projet cree")
  • client → api · POST previous_response_id: resp_001
  • api → store · recuperation automatique du contexte
  • api → client · 200 OK (id: resp_002, reponse enrichie)

Avantages majeurs de l'approche Responses API

Réduction drastique de la bande passante : le client n'envoie plus 50 Ko d'historique à chaque tour. Streaming unifié combinant texte, raisonnement (thinking tokens) et sorties d'outils en un seul flux. Outils managés côté serveur (navigateur web, interpréteur de code) exécutés sans infrastructure locale.
